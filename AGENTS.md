# Правила работы в AI Agents QA Demo

## Требования и границы работы

- Зафиксируй границы задачи и критерии приёмки до реализации. Один PR решает одну ограниченную задачу. Одна Issue может включать несколько PR.
- [Базовая линия КТ1](docs/KT1_BASELINE.md) фиксирует принятые материалы. Менять эти материалы, требования, сценарии S01–S06, согласованные бизнес-правила и визуальный эталон v0.2 можно только после отдельного согласования. Открытые решения требуют явного подтверждения перед реализацией зависящих от них правил.
- Указывай в каждом PR затронутые `REQ-XXX` и критерии приёмки. Если требования не затронуты, явно объясни почему. Обновляй документацию вместе с изменениями функциональности и добавляй содержательные проверки.
- В итоговом отчёте перечисли выполненные и пропущенные проверки и объясни причины пропусков. Документацию, описания Issue и PR и отчёты пиши по-русски, сохраняя идентификаторы и оригинальный текст ошибок.

## Разработка по спецификации (SDD)

- Для нового изменения используй OpenSpec по [процедуре SDD](docs/development/sdd-process.md). Указывай один `change-id` и связанную Issue. Ссылайся на существующие `REQ-XXX` и `S01–S06` без копирования базовой линии КТ1.
- До реализации зафиксируй отдельные утверждения пользователя для требований и сценариев, технического дизайна, задач и критериев проверки. Указывай версию рассмотренного артефакта. При изменении утверждённого материала снова согласуй затронутые стадии.
- Для каждого PR фиксируй срез задач и проверяемую связь «требование и сценарий → задача → тест или согласованная ручная проверка». Перед merge проверь результаты на точном SHA и соответствие утверждённому объёму. Структурная валидация OpenSpec сама по себе не подтверждает поведение.
- Один `change-id` может охватывать несколько PR. Синхронизируй дельту и архивируй изменение только после реализации и приёмки всех его задач.

## Git и GitHub

- Перед работой проверь корень репозитория, remote, путь worktree, ветку, полный HEAD и рабочее дерево, включая неотслеживаемые файлы. Сверь выбранный базовый коммит с актуальным источником. Если HEAD или удалённой базы ещё нет, явно зафиксируй это.
- Работай в отдельной ветке и при необходимости в отдельном worktree. Сохраняй незакоммиченные изменения. Прямой коммит в `main` допустим только для отдельно разрешённой минимальной инициализации пустого репозитория, когда без неё нельзя открыть первый PR.
- Фактически связывай каждый PR с Issue через GitHub Development и проверяй связь после создания PR и после merge. Merge и закрытие Issue требуют отдельного разрешения пользователя. Порядок работы описан в [процессе ревью](docs/development/review-process.md).
- Каждый PR, включая документационный, проходит независимое ревью точного SHA. Ревьюер работает в отдельной сессии Codex или как отдельный субагент, не участвует в реализации и не изменяет проверяемые файлы. После исправлений проводится ревью нового SHA.
- Проводится независимый системный аудит после максимум пяти слитых PR с рабочим кодом, раньше при существенных изменениях архитектуры, БД, авторизации или управления состояниями, а также перед релизом на точном release commit. См. [процесс аудита](docs/development/audit-process.md) и [журнал](docs/development/audit-log.md).

## AI-тестирование и безопасность

- Разделяй Logistics Agent, QA Agent и детерминированный QA Engine. Logistics Agent не получает эталонные ответы и внутренние правила оценщиков. Результаты QA Agent не подменяют детерминированные проверки.
- Каждый запуск сохраняет ID, конфигурацию, версии модели и промпта, трассу вызовов инструментов и проверяемые результаты. Различай симуляцию, replay и live в отчётах. Для live ограничивай стоимость, время и число попыток. Подробности в [правилах AI-тестирования](docs/development/ai-testing-rules.md).
- Секреты, токены и реальные персональные данные не включай в Git или публикуемые трассы. Операции удаления данных и сброса БД разрешены только в изолированном тестовом окружении с защитой от случайного запуска.
- Пользовательские файлы и чужие рабочие каталоги не удаляй и не перемещай без разрешения. Для временных файлов выбирай выделенный каталог задачи и фиксируй его абсолютный путь. Перед очисткой проверь принадлежность файлов, разрешённые пути и отсутствие выхода через ссылки или junction. Согласуй список удаляемых объектов и очищай их через корзину Windows. Если корзина недоступна, сохрани файлы и сообщи об этом.
