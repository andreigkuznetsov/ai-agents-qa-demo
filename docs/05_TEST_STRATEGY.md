# Стратегия тестирования AI Agents QA Demo

## Подход
Проверяем (1) обычный API и бизнес-правила, (2) корректность tool-driven поведения AI-агента, (3) независимость и точность оценщиков, (4) воспроизводимость испытаний. Везде выделяем ожидаемое и фактическое, evidence и версию проверок.

## Уровни
1. **Unit:** валидаторы бизнес-правил, idempotency, парсер tool calls, оценки/агрегация статусов.
2. **Integration:** FastAPI с реальной тестовой PostgreSQL, авторизация и создание обращений.
3. **Replay:** зафиксированные события, сбои и дефектные варианты без LLM; CI.
4. **Live agent:** реальные LLM-вызовы с закреплёнными fixture/prompt/model и повторными прогонами; не включать без лимитов.
5. **Evaluation of evaluator:** эталонный размеченный набор, включая ложные успехи, неизвестные исходы и противоречащие трассы.
6. **UI E2E:** запуск разрешённого режима, переход к двум трассам, доказательства, экспорт JSON.
7. **Security:** защита admin endpoints, секретов, prompt injection через untrusted tool output, чужих заказов, CORS/limiting.

## Таксономия ошибок
- `BUSINESS_RULE`: нарушение логистического правила.
- `TOOL_SELECTION`: неверный инструмент или недопустимый порядок.
- `UNAUTHORIZED_ACCESS`: доступ или запись без полномочий.
- `HALLUCINATED_SUCCESS`: сообщение об успехе без подтверждения.
- `IDEMPOTENCY`: дублирующие обращения.
- `RESILIENCE`: неверное поведение при timeout/500.
- `PROMPT_INJECTION`: следование недоверенным инструкциям из tool output.
- `EVALUATOR_ERROR`: ложный PASS/FAIL, утраченные evidence.
- `INFRASTRUCTURE`: недоступность сервиса / ошибки стенда.

## Test oracle и verdict
Результат работы тестируемого агента и результат QA Agent оцениваются независимо. Наличие записи в БД доказывается запросом к backend, а не сообщением модели. `ERROR` при сбое измерения; `INCONCLUSIVE` при недостаточном evidence. Критический deterministic FAIL доминирует над положительным QA Agent.

## Метрики (без придуманных результатов)
- Task Success Rate = число PASS / число завершённых оцениваемых live-запусков (исключённые ERROR/INCONCLUSIVE показывать отдельно).
- Policy Violation Rate = число live-запусков с policy violation / число запусков, на которых policy проверена.
- Precision/Recall QA Evaluator считать по размеченному gold set; отдельно TP/FP/FN/TN и определения положительного класса «обнаружен дефект».
- Stability: распределение вердиктов на повторных live-прогонах по одному сценарию.
- Latency/tokens/cost: сохранять факты; unknown не приравнивать к нулю.

## Экспериментальная дисциплина
До измерений фиксировать gold set, baseline, версии данных и prompts, правила оценки, число повторов и пороги. Если в ходе эксперимента меняются настройки, запускать новую серию и сохранять предыдущую.

## Fault injection
500, timeout, потерянный ответ после записи, конфликтующие ответы, injection в tool output, чужой заказ, неверный выбор инструмента. Fault привязан к run ID, все инъекции локальны и проверяемы. При исправном backend попытка нарушить правило не должна приводить к нарушению состояния; регистрировать попытку отдельно.

## Необходимые доказательства
`run_id`, `scenario_id`, `fixture_version/hash`, `agent_version`, `prompt_version`, `llm_model`, `tool events`, `api events`, `db before/after evidence`, `evaluator rubric and results`, `decision_reason`, `report hash`.
