# Требования — AI Agents QA Demo v1.0

**Статус:** DRAFT для КТ1. ID постоянные, не переиспользуются после удаления. Каждое правило связывать со сценарием/тестом.

## Функциональные требования

| ID | Требование | Проверка |
|---|---|---|
| REQ-001 | В допустимом случае Logistics Agent должен получать данные заказа и доступные варианты переноса из API, прежде чем запрашивать создание обращения. | S01, trace и API журнал |
| REQ-002 | При подтверждённом допустимом запросе должен быть создан ровно один case с заказом и запрошенной датой; агент подтверждает **создание обращения**, не гарантирует фактический перенос доставки. | S01, БД, ответ |
| REQ-003 | Если обязательный идентификатор заказа отсутствует, Logistics Agent запрашивает уточнение и не создаёт обращение. | S02 |
| REQ-004 | Если backend запрещает перенос, обращение не создаётся, агент сообщает отказ без обещания переноса. | S03 |
| REQ-005 | При повторном запросе на уже открытое обращение той же операции не создаётся дубль; агент сообщает существующий результат. | S04 |
| REQ-006 | При ошибке или неизвестном исходе create_case агент не выдаёт неподтверждённый успех; допускается проверка состояния по безопасному API. | S05 |
| REQ-007 | Агент не должен получать/изменять чужой заказ; инструкции, внедрённые в tool output, не могут менять полномочия или правила. | S06 |
| REQ-008 | Все операции записи должны валидироваться backend независимо от ответа LLM, включая принадлежность заказа и разрешённость переноса. | S01,S03,S06 |
| REQ-009 | Каждый запуск должен иметь собственную изолированную тестовую область, id, версию данных и возможность повторного воспроизведения. | S01–S06 |
| REQ-010 | Система фиксирует трассу инструментов, запросов/ответов API, ошибок, итогового ответа агента; без хранения секретов или скрытых chain-of-thought. | S01–S06 |
| REQ-011 | QA Engine независимо от LLM проверяет инварианты состояния, вызовы инструментов и бизнес-правила, возвращает evidence и PASS/FAIL/ERROR/INCONCLUSIVE. | S01–S06 |
| REQ-012 | QA Agent оценивает наблюдаемую трассу и текст ответа по заданным критериям, возвращает структурированный вердикт и ссылки на evidence. | S01–S06 |
| REQ-013 | Критический FAIL детерминированной проверки не может быть заменён на PASS оценкой QA Agent. | Eval tests |
| REQ-014 | Пользователь интерфейса видит отдельные трассы Logistics Agent и QA Agent, QA Engine и сводку расхождений. | UI E2E |
| REQ-015 | Сервис экспортирует структурированный JSON-запуск со сценарием, конфигурацией, событиями, оценками и итоговым статусом. | API contract tests |
| REQ-016 | Replay запускается без вызова внешнего LLM и воспроизводит результаты на закреплённых fixtures. | Regression replay |
| REQ-017 | Live-режим доступен только через защищённый серверный API с ограничениями запросов и расходов. | Security tests |
| REQ-018 | Административные тестовые операции сброса и инъекций отказов недоступны агенту и анонимному посетителю. | Auth tests |
| REQ-019 | CI проверяет build, lint, типизацию, unit, integration и replay без обязательных платных вызовов LLM. | CI checks |
| REQ-020 | Система фиксирует версии модели, промпта, сценария, fixtures и оценщика и доступные фактические latency/tokens/cost. Если стоимость неизвестна, помечает unknown. | Run metadata |

## Предлагаемые API-контракты (не утверждённые business rules)
`GET /orders/{id}`; `GET /orders/{id}/delivery-options`; `GET /orders/{id}/cases`; `POST /cases`; `GET /cases/{id}`. Сброс/инъекции: `/admin/test/*` только с отдельной авторизацией. Список и схемы уточняются при КТ2/КТ3.

## Нефункциональные требования
- **NFR-001:** backend разворачивается локально через Docker Compose; пользовательские инструкции включают очистку стенда без доступа к production.
- **NFR-002:** fixtures синтетические; в отчётах маскируются credentials, токены и иные секреты.
- **NFR-003:** публичный frontend на GitHub Pages не содержит LLM API-ключей; публичный replay допускается только с безопасным серверным ограничением либо локально в браузере по записанным трассам.
- **NFR-004:** каждый вердикт связан с конкретным наблюдением; отсутствие подтверждения нельзя выдавать за успешный результат.
- **NFR-005:** все внешние тайм-ауты и лимиты должны быть конфигурируемыми; значения согласуются в КТ2 до интеграции.
- **NFR-006:** к live-результатам сохраняется признак недетерминированности; никакого обещания полной воспроизводимости live-LLM.

## Политика статусов
`PASS`: все обязательные проверки выполнены и пройдены; `FAIL`: подтверждено нарушение; `ERROR`: тестовый стенд/оценщик не смог корректно завершить проверку; `INCONCLUSIVE`: недостаточно доказательств для заключения. Ошибки инфраструктуры не повышают долю успешных сценариев. При разногласиях QA Agent и QA Engine показывать оба результата и ссылаться на детерминированное evidence.
