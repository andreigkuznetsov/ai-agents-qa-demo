# КТ3. Решения DEC-01–07 для Logistics API Simulator

Редакция 2 от 23.11.2026. Решения утверждены пользователем в чате Codex. План с одним change-id и четырьмя PR утверждён отдельно. Редакция 2 добавляет адресные уточнения к Requirements. [Журнал Issue №14](https://github.com/andreigkuznetsov/ai-agents-qa-demo/issues/14)

| Решение | Утверждённое правило КТ3 | Отличие или уточнение к исторической КТ1 |
| --- | --- | --- |
| DEC-01 | Запрос на перенос оформляется как обращение `DELIVERY_RESCHEDULE` со статусом `OPEN`. Исходная дата доставки сохраняется. Закрытие и повтор после закрытия вне КТ3. | Реестр КТ1 уже предполагал обращение вместо смены даты. Тип, статус и пределы жизненного цикла конкретизированы. |
| DEC-02 | Допустимы два синтетических состояния заказа, `ACTIVE` и `TRANSFER_BLOCKED`. Операция разрешена только в `ACTIVE` и при выполнении остальных условий. | Закрыт вопрос о списке состояний. Исторический условный код `TRANSFER_BLOCKED` подтверждён. |
| DEC-03 | Непрозрачный синтетический токен сервер связывает с `client_id` и `run_id`. Данные body не дают полномочий. | Контекст исходного предложения дополнен границей запуска. `run_id` без действительной аутентификации не даёт прав. |
| DEC-04 | Ключ запроса и уникальность открытого бизнес-обращения контролируются отдельно. Новый case возвращает `201`, существующий — `200`, конфликт повторно использованного ключа — `409`. Design учитывает конкуренцию и согласованную запись ключа и результата. | Исходное предложение различало ключ и бизнес-дубликат. КТ3 уточняет наблюдаемое поведение и ограничивает его открытыми обращениями. |
| DEC-05 | При неизвестном исходе предусмотрена одна авторизованная сверка по исходному ключу в границах клиента и запуска. Автоматического повторного `POST` нет. Найденный результат, отсутствие результата и недоступность сверки различаются. | КТ1 допускала безопасную проверку и оставляла политику повторов открытой. Для КТ3 принято более узкое правило. |
| DEC-06 | Для отсутствующего, чужого и недоступного из другого запуска объекта используется единый публичный `404`. Для отсутствующей или недействительной аутентификации используется `401`. | КТ1 требовала ответа без раскрытия чужих данных и оставляла HTTP-статус открытым. Противоречия с S06 не обнаружено. |
| DEC-07 | `delivery-options` возвращает даты из версионированных синтетических fixtures. Для номинальных сценариев используется `2026-11-26`. | Демонстрационная дата КТ1 закреплена для fixtures. Это не правило реальной логистической системы. |

## Согласованные уточнения Requirements

- Для DEC-02–04 и DEC-06 согласованы `401 UNAUTHENTICATED`, единый `404 RESOURCE_NOT_FOUND`, `409 ORDER_TRANSFER_BLOCKED`, `422 DELIVERY_DATE_NOT_ALLOWED`, `422 VALIDATION_ERROR`, `409 IDEMPOTENCY_KEY_CONFLICT`, `201` для нового и `200` для существующего case. Равенство публичного тела `404` обязательно для отсутствующего, чужого и недоступного из другого запуска ресурса.
- Для DEC-04 повтор того же ключа и содержимого требует действующего доступа. Он возвращает сохранённый результат без повторной проверки изменившихся бизнес-условий. Новый ключ требует актуальной проверки состояния заказа и даты.
- Для DEC-05 сверка возвращает `200 FOUND`, `200 NOT_FOUND` или `503 RESULT_CHECK_UNAVAILABLE`. `NOT_FOUND` означает отсутствие подтверждения на момент сверки, включая незавершённую запись. Этот исход не доказывает отказ исходного запроса. Автоматический повтор `POST` исключён.
- Для fixtures по DEC-07 повторная инициализация запуска требует совпадения версии и контрольной суммы содержимого. При любом несовпадении состояние сохраняется и возвращается контролируемый внутренний отказ. Четыре поля `runs` сохраняются.

Исторические статусы DEC и примеры прототипа относятся к моменту фиксации КТ1. Они сохранены. Полная редакция Requirements, включая точные маршруты, поля и нормализацию запроса, ожидает окончательного утверждения.
