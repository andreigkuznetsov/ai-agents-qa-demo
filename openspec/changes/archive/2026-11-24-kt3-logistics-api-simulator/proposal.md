# КТ3. Logistics API Simulator

- Change-id `kt3-logistics-api-simulator`.
- [Issue №14](https://github.com/andreigkuznetsov/ai-agents-qa-demo/issues/14).
- База КТ2 `dedd5c353010b89fecbf0969b8034003c13b256e`.
- Стадия Requirements. Декомпозиция на четыре PR и перечисленные ниже статусы и коды записи и сверки согласованы. Полная редакция Requirements ожидает утверждения.

## Why

Для КТ3 нужен локальный API, который воспроизводимо моделирует заказы и обращения и сам обеспечивает ограничения на чтение и запись. Его результат будет проверяться по ответам API и состоянию PostgreSQL и станет основой для последующего тестирования агентов.

## What Changes

- Версионированные синтетические fixtures, логическая изоляция по запуску и серверная аутентификация для клиента в пределах запуска.
- Чтение своего заказа и доступных дат, запрет операции для `TRANSFER_BLOCKED`, единый публичный ответ для недоступного ресурса.
- Чтение и создание `DELIVERY_RESCHEDULE` со статусом `OPEN`, сохранение исходной даты доставки, независимый контроль идемпотентности запроса и бизнес-дубликата.
- Авторизованное чтение результата по исходному ключу и интеграционные проверки неизвестного исхода. Тестовый механизм отказов действует только во внутренней инфраструктуре, с границей для будущего QA Orchestrator.

## Capabilities

### New Capabilities

- `logistics-api-simulator` — локальное поведение API заказов и обращений, изоляция, авторизация и воспроизводимые проверки отказов. [Дельта Requirements](specs/logistics-api-simulator/spec.md)

### Modified Capabilities

Действующие `postgres-runtime`, `run-store` и `compose-acceptance` сохраняются. Таблица `runs` сохраняет четыре утверждённых поля. Версия fixtures относится к набору доменных данных, а не к `runs.schema_version`.

## Impact

После прохождения ворот изменение затронет доменные API, доменное хранение в общей PostgreSQL, тестовые fixtures и интеграционные проверки. Публичный доступ к тестовому управлению, закрытие обращений, повтор после закрытия, изменение расписания доставки, боевые данные, Logistics Agent, QA Agent, QA Engine, полный replay и общий механизм fault injection вне КТ3. Исторические материалы КТ1, прототип v0.2 и нормативные спецификации КТ2 сохраняются. ## HTTP-контракты и статус согласования

Для записи и сверки согласованы статусы и коды таблицы, включая `200 FOUND`, `200 NOT_FOUND` и `503 RESULT_CHECK_UNAVAILABLE`. Для чужого, отсутствующего и недоступного из другого запуска ресурса согласовано одинаковое публичное тело `404 RESOURCE_NOT_FOUND`. Форма ошибки `{"error":{"code":"CODE"}}` предлагается без отладки и сведений о владельце. Предлагаемый `CASE` содержит `case_id`, `order_id`, `requested_date` (ISO-дата), `operation_type` со значением `DELIVERY_RESCHEDULE` и `status` со значением `OPEN`. Владелец и запуск определяются сервером. Точные маршруты, размещение ключа и схемы тел остаются частью этой редакции Requirements на утверждение.

Предлагаемые маршруты. Чтение заказа и вариантов — `GET /orders/{order_id}` и `GET /orders/{order_id}/delivery-options`. Создание — `POST /cases` с телом `{"order_id":"12345","requested_date":"2026-11-26","operation_type":"DELIVERY_RESCHEDULE"}` и заголовком `Idempotency-Key`. Чтение обращений — `GET /orders/{order_id}/cases` и `GET /cases/{case_id}`. Сверка — `GET /orders/{order_id}/case-result` с исходным `Idempotency-Key`. Для чтения заказа предлагаются `order_id`, `status`, `scheduled_delivery_date`. Для чтения вариантов — `order_id`, `eligible`, `reason_code` и `dates` (список ISO-дат). Для статуса `TRANSFER_BLOCKED` список пуст, причина `ORDER_TRANSFER_BLOCKED`. Для `ACTIVE` без допустимых дат список пуст, причина `NO_AVAILABLE_DATES`. При наличии вариантов `eligible=true` и `reason_code=null`. Чтение списка обращений возвращает `{"cases":[CASE,...]}`.

| Случай | HTTP | Код | Тело | Эффект на доменную БД |
| --- | --- | --- | --- | --- |
| Неаутентифицированный запрос | `401` | `UNAUTHENTICATED` | Ошибка | Нет. |
| Чтение своего заказа, вариантов или обращений | `200` | — | Заказ, варианты, список или `CASE` по запрошенному маршруту | Чтение. |
| Нет заказа, заказ чужой или вне запуска. То же правило для недоступного case | `404` | `RESOURCE_NOT_FOUND` | Одинаковая ошибка | Нет. |
| Новый запрос записи для `TRANSFER_BLOCKED` | `409` | `ORDER_TRANSFER_BLOCKED` | Ошибка | Case и привязка ключа не создаются. |
| Запрошенная дата отсутствует в доступных датах | `422` | `DELIVERY_DATE_NOT_ALLOWED` | Ошибка | Case и привязка ключа не создаются. |
| Нет обязательного поля или ключа, неверный формат | `422` | `VALIDATION_ERROR` | Ошибка | Case и привязка ключа не создаются. |
| Новое обращение | `201` | — | `CASE` | Один новый case и привязка ключа. Исходный заказ сохраняется. |
| Тот же ключ и то же содержимое | `200` | — | Тот же `CASE` | Без изменений. |
| Новый ключ, открытый бизнес-дубликат | `200` | — | Существующий `CASE` | Новый case не создаётся. Новый ключ связывается с существующим результатом. |
| Тот же ключ, другое содержимое | `409` | `IDEMPOTENCY_KEY_CONFLICT` | Ошибка | Исходный case и привязка сохраняются. |
| Сверка нашла результат | `200` | — | `{"outcome":"FOUND","case":CASE}` | Чтение. |
| Сверка выполнена, в текущем контексте результата нет, включая ещё не зафиксированную запись | `200` | — | `{"outcome":"NOT_FOUND","case":null}` | Чтение. Отсутствие подтверждения на момент сверки не доказывает отказ или откат первоначального POST. |
| Сверка недоступна | `503` | `RESULT_CHECK_UNAVAILABLE` | Ошибка | Связанные данные не меняются. Исход исходной операции остаётся неизвестным. |

При невалидной аутентификации сверка возвращает `401`, для недоступного заказа — единый `404`. Для доступного заказа ключ без результата в текущем контексте одинаково обрабатывается независимо от его отсутствия или наличия в другом контексте.

## Порядок проверки POST и равенство запроса

1. Аутентифицировать запрос, получить доверенные `client_id` и `run_id`. Невалидная аутентификация возвращает `401` до проверки ключа.
2. Проверить наличие и формат ключа и бизнес-полей, затем подтвердить доступ к указанному заказу. Для синтаксической ошибки применяется `422 VALIDATION_ERROR`, для недоступного заказа — единый `404`. Поиск ключа и сравнение содержимого выполняются после подтверждения доступа.
3. Проверить ключ в области `(run_id, client_id, operation_type, key)`. Равенство содержимого определяется по тройке `(order_id, requested_date, operation_type)` после валидации. Сравниваются точный строковый идентификатор заказа без приведения к числу или изменения регистра, действительная календарная дата в форме `YYYY-MM-DD` и точное значение `DELIVERY_RESCHEDULE`. Порядок полей, пробелы форматирования JSON и эквивалентное JSON-экранирование не влияют на равенство.
4. Для уже сохранённого ключа с тем же содержимым вернуть прежний `CASE` с `200`, сохранив текущее состояние БД. При другом содержимом вернуть `409 IDEMPOTENCY_KEY_CONFLICT`. В обеих ветках изменившиеся состояние заказа и доступность даты повторно не применяются.
5. Для нового ключа заново проверить `ACTIVE` и допустимую дату до создания case или привязки ключа к открытому дубликату. Бизнес-область определяется отдельно по `(run_id, client_id, order_id, requested_date, operation_type)`. Гарантии при конкуренции остаются требованиями, способ их реализации относится к Design.

## Повторная инициализация fixtures

Повтор для инициализированного запуска допускается только при совпадении версии и контрольной суммы всего фактически загружаемого содержимого. Совпадение обоих значений сохраняет имеющееся состояние без дублей. При несовпадении любого значения инфраструктура возвращает контролируемый внутренний отказ и сохраняет данные запуска и других запусков. Представление метаданных и способ вычисления суммы относятся к Design. Контракт четырёх полей `runs` сохраняется.

## Вопросы для утверждения Requirements

1. **Формы HTTP.** Подтвердить маршруты, `Idempotency-Key`, поля успешных ответов и единое тело ошибки. Статусы и коды из явного согласования повторного выбора не требуют.
2. **Значения ключей и полей.** Подтвердить область ключа и правила равенства содержимого. Хранение и атомарность относятся к Design.
3. **Временные пределы.** Численные бюджеты бизнес-вызовов пока не утверждены. Рекомендация — определить их отдельным решением с учётом измерений, сохраняя бюджеты КТ2. Контракт сверки сохраняет одну попытку чтения без автоматического повторного `POST`.
