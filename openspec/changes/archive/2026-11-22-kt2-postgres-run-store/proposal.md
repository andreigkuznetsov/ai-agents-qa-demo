# Proposal

- **Change-id:** `kt2-postgres-run-store`
- **GitHub Issue:** [№3 — архитектура и локальный инфраструктурный каркас](https://github.com/andreigkuznetsov/ai-agents-qa-demo/issues/3), КТ2 PR 2
- **База:** `48d132542189eb70efb26149f903a88972c6ec3d`
- **Стадия:** Requirements. Ожидает утверждения.

## Why

PR 1 дал HTTP-процесс FastAPI и liveness. Для следующего среза нужен воспроизводимый локальный запуск с PostgreSQL, чтобы проверить порядок миграции, доступность нужной версии схемы и сохранение технических записей запусков.

## What Changes

- Docker Compose запускает локальные PostgreSQL и API. Отдельная миграция Alembic завершается до старта API. Повторный запуск миграции безопасен для текущей схемы и записей.
- Слой хранения создаёт и читает синтетические записи `runs` по `run_id`. В записи четыре поля: UUID `run_id` как первичный ключ, `schema_version`, `created_at` в UTC и технический статус `CREATED`. В общей PostgreSQL `run_id` задаёт логическую границу тестовых запусков. Проверку изоляции доменных сущностей проводим после их появления в КТ3/КТ6.
- `GET /health/ready` и `GET /healthz` проверяют доступ к PostgreSQL и ожидаемую ревизию миграции. `GET /health/live` сохраняет контракт PR 1 и не зависит от PostgreSQL.
- Интеграционные проверки PR 2 используют реальную тестовую PostgreSQL и синтетические записи. Сквозной smoke-тест Compose в CI и эксплуатационная инструкция остаются в PR 3.

## Capabilities

### New Capabilities

- `postgres-runtime`: локальный запуск, порядок миграций, сетевые границы и готовность API.
- `run-store`: минимальная запись запуска, адресация по `run_id` и сохранение данных между остановками.

### Modified Capabilities

Нет. Базовый контракт liveness из PR 1 сохраняется.

## Impact

При реализации изменятся серверная конфигурация, локальный Compose, миграции, слой хранения и health API. Используется ранее согласованный стек FastAPI, PostgreSQL, SQLAlchemy, psycopg и Alembic. PostgreSQL не публикует порт на хост, локальный HTTP по умолчанию доступен только на loopback.

В scope входят только инфраструктурные возможности и проверки этого PR. Утверждённые материалы КТ1, прототип v0.2, DEC-01–07, бизнес-логика заказов и обращений, агенты, оценщики, внешние LLM и продуктовые API вне scope. Схема `runs` сохраняет минимальный состав. Показатели моделей, промптов, токенов, стоимости и качества в этом срезе не формируются.

## Открытые вопросы перед Design

| Вопрос | Предложение для рассмотрения |
| --- | --- |
| Версия PostgreSQL, форматы и версии дополнительных зависимостей | Выбрать один поддерживаемый мажор PostgreSQL, зафиксировать точную версию и digest образа, проверить совместимость с уже закреплённым Python и lock-файлом. |
| Представление четырёх полей и способ их заполнения | Рассмотреть положительное целое `schema_version` с первым значением `1`, PostgreSQL `timestamptz` с чтением в UTC и ограничение записываемого приложением статуса до `CREATED`. Согласовать, где формируются UUID и timestamp. |
| Определение ожидаемой ревизии и параметры отказа | Рассмотреть сверку текущей ревизии БД с ревизией миграций из сборки. Согласовать бюджеты старта, подключения, запроса readiness и восстановления, а также малый пул соединений. |
| Контракт тела readiness и проверка ошибок | Сохранить существующий формат liveness. Для readiness согласовать короткий ответ об общем состоянии и одинаковый контракт для обоих маршрутов. Ошибку миграции и расхождение ревизий проверять на отдельном синтетическом стенде. |
| Роли и сетевые настройки в локальном Compose | Определить конфигурацию учётных данных для мигратора и API, границы прав, HTTP bind и способ доказать отсутствие опубликованного порта PostgreSQL. |

Предложения выше не утверждают дизайн. Принцип общей PostgreSQL и адресации по `run_id` уже принят в [решениях КТ2](../../../docs/development/kt2-architecture.md). Конкретные параметры DEC-01–07 этим изменением не утверждаются.
