## Why

PR 1 подтвердил сборку контейнера API и liveness. PR 2 подтвердил контракты PostgreSQL, миграций, `runs` и health в изолированных сценариях. Для приёмки КТ2 нужно доказательство одного пользовательского пути из чистого checkout и воспроизводимая инструкция для Windows и Linux.

## What Changes

- Один сквозной smoke в CI проверяет поддерживаемый путь запуска из чистого checkout. Он фиксирует миграцию до старта API, health и сетевые границы, сохранение записи через обычную остановку и повторный запуск, потерю и восстановление готовности и диагностируемый отказ миграции на отдельном стенде.
- Инструкция описывает запуск, остановку с сохранением данных и диагностику на Windows с Docker Desktop и Linux с Docker Compose. На Linux доказательством служит автоматический сквозной прогон в GitHub Actions с реальным Docker Compose. На Windows требуется отдельное подтверждение фактического выполнения инструкции в Docker Desktop.
- Приёмка объединяет доказательства трёх PR. Статус КТ2 подтверждает пользователь после выполнения применимых критериев и независимого ревью точного SHA PR 3.

## Capabilities

### New Capabilities

- `compose-acceptance` — воспроизводимая сквозная проверка Compose-стенда, безопасные действия оператора и пригодные для приёмки доказательства.

### Modified Capabilities

Нет. `postgres-runtime` и `run-store` закрепляют принятые контракты PR 2. В каталоге `openspec/specs` действующих возможностей пока нет. Новый spec ссылается на стабильные AC/SC активных дельт, поэтому эти ссылки сохранят смысл после переноса требований в действующие спецификации.

## Impact

В будущий PR 3 входят CI, минимальные средства проверки и инструкция. Контракты API, четыре поля `runs`, роли, схема, версии и бюджеты D-PG-01–04 сохраняются. За пределами среза остаются агентная и бизнес-логика, внешние LLM, полная изоляция доменных данных, replay, публикация стенда, восстановление снимка, переход между различными релизными ревизиями и удаление пользовательских томов. Нормативные материалы КТ1, прототип v0.2, S01–S06 и открытые DEC-01–07 сохраняются. Sync/Archive предыдущего изменения — отдельная операция по разрешению пользователя.

## Связь с проверками PR 2

Сквозной набор повторяет только критические границы единого пользовательского пути. Повторная миграция и совпадение записи проверяются внутри одного цикла остановки, потеря БД проверяется на уже работающем API, отрицательный запуск использует один управляемый отказ миграции на отдельном проекте. Дрейф ACL, транзакционный rollback и `GRANT`, несовпадение ревизии, дубликаты, детальные задержки, исчерпание пула и отмена продолжают проверяться принятыми интеграционными тестами PR 2. Технические бюджеты и контрактные статусы берутся из утверждённого D-PG-01–04.

## Риски и вопросы перед Design

| Вопрос | Предложение для согласования |
| --- | --- |
| Стабильность CI и конкуренция за ресурсы | Привязать каждый прогон к собственному Compose-проекту с пустым томом, использовать ограниченное ожидание и отделить время checkout и сборки от согласованных бюджетов старта и health. Точные механизмы изоляции и измерения выбрать в Design. |
| Воспроизводимый отказ миграции | Проверить одну причину на отдельном синтетическом стенде. В Design выбрать способ инъекции и безопасные поля, по которым оператор различает стадию отказа. Подробные сбои Alembic, прав, тайм-аутов и пула уже проверены в PR 2. |
| Windows и Linux | Уточнить среду, ответственного и форму подтверждения фактического прогона на Windows. При недоступности Windows Docker Engine зафиксировать `NOT VERIFIED`, причину и влияние на полную приёмку КТ2. Результаты Linux и моки учитываются только в пределах своих проверок. |
| Согласованность инструкции и CI | Проверять тот же поддерживаемый порядок действий, с различиями в синтаксисе оболочек и способе фиксации результатов. Выбрать место инструкции и объём публикуемой диагностики в Design. |
| Завершение предыдущей дельты | Предложить отдельный Sync/Archive `kt2-postgres-run-store` после разрешения пользователя. Дополнительное условие для утверждения текущих Requirements не требуется, так как наборы идентификаторов и возможности не пересекаются. |
