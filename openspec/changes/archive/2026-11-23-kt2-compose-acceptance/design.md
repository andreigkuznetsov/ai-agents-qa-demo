# Design

## Context

КТ2 PR 3 · `kt2-compose-acceptance` · [Issue №3](https://github.com/andreigkuznetsov/ai-agents-qa-demo/issues/3). Пользователь утвердил Design в редакции `df2d5ca9a7670389591bae1c739f8900ddac123d` с уточнениями по доказательствам и Windows-приёмке 23.11.2026. Утверждённые [proposal](proposal.md) и [Requirements](specs/compose-acceptance/spec.md) зафиксированы в коммите `1bc6c34b361c9b70d677b58fc1ba717f7b7885ca`. База проектирования — `main` на `1d58c324beb01dc5ec3ea51491fec308eea6bc6b` после [PR №10](https://github.com/andreigkuznetsov/ai-agents-qa-demo/pull/10).

Стенд опирается на действующие [postgres-runtime](../../specs/postgres-runtime/spec.md), [run-store](../../specs/run-store/spec.md) и утверждённый [Design PR 2](../archive/2026-11-22-kt2-postgres-run-store/design.md). [`compose.yaml`](../../../compose.yaml) задаёт топологию и публикацию портов. [`scripts/start-local.py`](../../../scripts/start-local.py) уже ограничивает запуск и запускает мигратор до API. PR 3 будет проверять этот путь в CI и в инструкции. Существующие тесты Backend CI остаются доказательствами для ACL, транзакционного отката, несовместимой ревизии, дубликатов, тайм-аутов, пула и отмены.

## Goals / Non-Goals

- Один поддерживаемый путь для запуска, остановки и повторного запуска стенда в Linux CI и на Windows с Docker Desktop. Доказательства для платформ хранятся раздельно на одном SHA кандидата.
- Сохраняются версии, схема, роли `qa_admin`, `qa_migrate`, `qa_api`, сетевые границы и четыре поля `runs` — `run_id`, `schema_version`, `created_at`, `status`. Проверка использует `RunStore` под ролью API и синтетический UUID. Публичный маршрут записи для smoke не вводится.
- Восстановление снимков, переход между выпущенными ревизиями, конкурентное обновление, проверка production и доменная изоляция остаются вне среза. Для обслуживающего обновления инструкция сохраняет требования остановить API, проверить резервную копию и исключить параллельные операции. В сценарии повторного запуска используется та же сборка.

## Decisions

### D-CAF-01. Общий путь запуска и изоляция

Предлагается один вспомогательный драйвер на стандартной библиотеке Python для CI и локального приёмочного запуска. Он вызывает фактические команды, описанные в одной инструкции, и собирает наблюдения. Инструкция содержит общий порядок и раздельные примеры запуска в PowerShell и Linux shell. Обычный локальный запуск по инструкции может выполняться вручную. Подтверждение Windows получают через запуск драйвера по Windows-инструкции на реальной машине.

| Стадия | Общий порядок | Платформенная часть |
| --- | --- | --- |
| Предварительная проверка | Сверить чистый checkout и полный SHA, наличие Python, Docker Engine, Compose v2, Linux container engine и разрешённого локального контекста. Получить отдельный временный конфигурационный файл и собственный идентификатор проекта. | В GitHub Actions использовать новый hosted Linux runner. На Windows проверить, что выбран локальный Docker Desktop, его Linux engine доступен, а каталог checkout доступен для bind mount. |
| Сборка и запуск | Собрать `api` через исходный Compose из checkout с закреплёнными образами и зависимостями, использовать уникальный тег для `api` и `migrate`. Вызвать существующий `start-local.py` с явными `--project` и `--env-file`. | Путь к Python и кавычки в PowerShell и Linux shell различаются. Подпроцессы получают аргументы отдельным списком. |
| Наблюдение и повтор | Проверить порты, HTTP, миграцию и запись. Выполнить `docker compose stop` с теми же параметрами проекта и файла конфигурации, проверить остановку и повторить запуск. После каждого старта заново определить выданный HTTP-порт. | Доступ к HTTP идёт через `127.0.0.1`. Проверку PostgreSQL и `RunStore` выполнять в контейнерах проекта через `docker compose exec -T`, чтобы путь работал и в сети Docker Desktop. |
| Диагностика | Различать недоступный движок или ошибочный контекст, неполную конфигурацию, ошибку публикации HTTP, недоступную БД, отказ миграции и сбой проверки HTTP. Проверять состояние и код нужного сервиса. | На Windows инструкция добавляет проверку статуса Desktop и доступности каталога. На Linux — проверку доступа к локальному daemon. Советы по чужому занявшему порт процессу ограничены диагностикой и выбором другого порта. |

Для автоматически проверяемого запуска использовать `QA_HTTP_PORT=0` и извлекать фактическое сопоставление из состояния контейнера, как в PR 2. Проверка требует привязку к `127.0.0.1` и отсутствие опубликованного порта PostgreSQL. Обычный пример в инструкции сохраняет `127.0.0.1:8000`. Проект и именованный том создаются для конкретной попытки. Позитивная и негативная ветви прогонов CI используют разные проекты, тома и временные файлы. Повторный запуск в позитивном сценарии использует прежний проект и тот же том. [Docker contexts](https://docs.docker.com/engine/manage-resources/contexts/) · [Docker Compose stop](https://docs.docker.com/reference/cli/docker/compose/stop/)

### D-CAF-02. Сквозной Linux smoke и управляемый отказ миграции

Предлагается отдельная проверка GitHub Actions на `ubuntu-24.04`, в чистом checkout точного HEAD при `pull_request`. Workflow сверяет `git rev-parse HEAD` с SHA кандидата и использует только синтетические credentials, с правами токена только на чтение репозитория. Существующий Backend CI продолжает выполнять детальные проверки. Жизненный цикл smoke идёт последовательно в одном runner, так как сохранность тома и экземпляра API проверяется между шагами. [GitHub-hosted runners](https://docs.github.com/en/actions/concepts/runners/github-hosted-runners)

1. В позитивном проекте проверить отсутствие предыдущих ресурсов, собрать образ из checkout и запустить стенд. Снять ожидаемую ревизию из конкретного образа и прочитать фактический head внутри сети проекта. Сверить код `0` и время завершения `migrate` с временем запуска `api`. Проверить три маршрута с хоста, внутренний доступ к БД и привязки портов.
2. Через `RunStore` создать синтетическую запись и сохранить её четыре значения. Штатно остановить проект, подтвердить остановку `api` и `db` и сохранение тома, затем запустить ту же сборку. Снять служебный результат очередной миграции и прочитать запись через `RunStore`. Первичный ключ и результат чтения подтверждают единственность, повторный прогон сверяет UUID и все четыре значения без создания ещё одной строки.
3. На готовом API штатно остановить только БД. Зафиксировать liveness и оба readiness-ответа. Запустить ту же БД и подтвердить возврат обоих readiness в `200`. Сверить идентификатор и время запуска API до и после, чтобы подтвердить отсутствие перезапуска.
4. Для негативного сценария создать второй, одноразовый CI-проект с пустым томом и тем же образом. Поднять только `db`, дождаться здорового состояния и проверить, что `qa.runs` и `qa.alembic_version` ещё отсутствуют. Внутри именно этого `db` под bootstrap-ролью изменить владельца тестовой схемы `qa` на `qa_admin`. Перед вмешательством подтвердить метку проекта, принадлежность и свежесть тома, отсутствие API и запуск на одноразовом Linux runner. Такой источник ошибки уже проверен в PR 2. Он проходит стадию готовности PostgreSQL и попадает в существующую проверку владельца до DDL. Запустить неизменённый поддерживаемый путь с конфигурацией негативного проекта и проверить состояние `migrate` с кодом `1`, безопасную категорию отказа миграции, отсутствие запуска API и отсутствие обеих таблиц после отказа. Любая иная причина завершения, включая ошибку подготовки или тайм-аут, считается неуспехом сценария. Инъекция живёт только в CI и не доступна из штатной команды Windows или Linux.

Бюджеты PR 2 сохраняются. Старт — `90 с`, из них до `40 с` на БД, `30 с` на процесс миграции и `15 с` на готовность API. Readiness — `3 с` с согласованным допуском измерения `500 мс`. Пул, подключение, SQL и миграционные lock/statement timeout остаются по D-PG-03. Для наблюдения восстановления предлагается до `40 с` на готовность БД и до `15 с` на возврат readiness после неё. Отдельные HTTP-ожидания и повторы используют монотонный дедлайн, обновляют остаток времени и завершаются при его исчерпании. Пригодный HTTP-ответ сверяется сразу, повторы допустимы только в ожидаемом окне перехода состояния. Checkout и сборка имеют отдельный предел GitHub Actions. Предлагается общий предел `15 мин` на job с измерением фаз в первом прогоне. Значения приложению не переопределяются ради прохождения CI.

### D-CAF-03. Доказательства на точном SHA и статус Windows

Драйвер формирует структурированный отчёт JSON с кратким читаемым резюме. Общие обязательные поля — точный полный commit SHA, платформа, версии инструментов, фактические результаты проверок и итоговый статус. Также сохраняются версия формата, результат сверки чистоты checkout и preflight, тип Docker-контекста, имя тестового проекта, идентификаторы образа и тома, метки времени и итог по сценариям. Для каждого шага сохраняются команда с безопасными аргументами, код завершения, длительность по монотонным часам, ожидаемая и фактическая категории результата. В Linux-доказательство входят идентификатор и ссылка на GitHub Actions. В Windows-доказательство входят подтверждённый локальный Docker Desktop, фактические версии Desktop, Docker Engine и Compose, а также результаты запуска опубликованных Windows-команд. Если конкретная версия Desktop недоступна через CLI, оператор подтверждает её через интерфейс Desktop и отчёт помечает источник значения. Версии или результаты, недоступные в случае `NOT VERIFIED`, обозначаются как недоступные с указанием причины.

| Статус Windows | Основание | Влияние на приёмку |
| --- | --- | --- |
| `PASS` | На SHA кандидата пройден preflight реального Docker Desktop и выполнены все обязательные действия SC-CAF-005. Отчёт содержит фактические результаты и проходит собственную проверку полноты. | Windows-критерий подтверждён. Linux по-прежнему подтверждается отдельно. |
| `FAIL` | Фактический прогон начался, обязательный шаг завершился ошибкой, ожидание истекло либо результат не соответствует контракту. | Windows-критерий не выполнен. В отчёте остаётся первый значимый отказ. |
| `NOT VERIFIED` | Docker Engine недоступен, Desktop или подходящий контекст не подтверждён, подходящая среда отсутствует либо запуск не состоялся. | Отчёт указывает причину и отсутствие доказательства полной приёмки КТ2. Linux CI и моки имеют отдельный статус. |

Linux сохраняет очищенный JSON и резюме в GitHub Actions с явно заданным `retention-days: 30`, включая случаи ошибок, когда отчёт безопасно сформирован. Проверка публикует только заранее разрешённые файлы, сверяет SHA и обязательные поля и завершает job ошибкой при отсутствии обязательного Linux-доказательства. Резюме связывает артефакт и CI с точным SHA. Отсутствие обязательного отчёта исключает `PASS` для соответствующей платформы.

Docker Desktop установлен на компьютере пользователя и обычно выключен. После успешного Linux CI на SHA кандидата Codex в VS Code сообщает пользователю о необходимости запустить Docker Desktop и ждёт подтверждения готовности. Затем Codex в VS Code сверяет тот же SHA, рабочее дерево и доступность локального Desktop в режиме Linux-контейнеров и выполняет согласованную Windows-инструкцию в отдельном тестовом Compose-проекте. До подтверждённого фактического прогона Windows имеет статус `NOT VERIFIED`. Для полной приёмки нужны результаты обеих платформ.

Windows-отчёт первоначально сохраняется в `local-runs/kt2-pr3/`, вне Git. После проверки на отсутствие секретов очищенный отчёт прикладывается к Issue №3 либо сохраняется как отдельный доступный артефакт со ссылкой из Issue. Сырые логи, DSN, credentials и диагностические данные, раскрывающие секреты, не попадают в Git или опубликованные доказательства. Если после Windows-прогона меняются код, конфигурация или инструкция, влияющие на результат, затронутые проверки выполняются повторно на новом SHA. В итоговую приёмку входят доказательства, сверенные с итоговым кандидатом. [Хранение артефактов GitHub Actions](https://docs.github.com/en/actions/tutorials/store-and-share-data)

### D-CAF-04. Защита проектов, томов и секретов

- Перед операциями изменения выбрать и закрепить локальный контекст с Linux engine. Отклонять удалённые Docker endpoints, внешние overrides `DOCKER_HOST`, `COMPOSE_FILE`, `COMPOSE_PROJECT_NAME` и неожиданные переопределения `QA_*`. Проект, Compose-файл и конфигурация передаются явно. Все процессы от сборки до остановки используют один и тот же проверенный контекст. Windows не запускает негативную инъекцию.
- Автоматизация использует сгенерированные имена и проверяет отсутствие коллизий по Compose labels до создания. Перед остановкой, обращением к тестовому тому или негативной инъекцией сверяются идентификаторы и принадлежность проекта. При несовпадении защита завершает действие ошибкой. Штатная остановка и обработчик завершения могут остановить только проверенные сервисы текущего запуска, с ограничением времени. Сохранённый код исходной ошибки не подменяется успешной остановкой.
- Локальная инструкция сохраняет том при обычной остановке и описывает риск удаления и отдельное согласование. Драйвер не выполняет удаление томов и глобальную очистку. Изолированные данные Linux CI остаются в одноразовой машине до завершения job. Windows сохраняет тестовый том для повторного запуска с тем же проектом. Дальнейшее удаление согласуется отдельно.
- Credentials случайные и уникальные для проекта. Они передаются через временный конфигурационный файл вне checkout или замкнутое окружение процесса. Отчёт строится из разрешённых полей. В нём допустимы коды, публичные health-тела, значения синтетической записи, время запуска, безопасные категории и отфильтрованные свойства Docker. Сырые `docker inspect`, `docker compose config`, env, DSN и необработанные логи не публикуются. Перед записью и публикацией отчёт проверяется на фактические значения синтетических секретов и на наличие запрещённых полей. При нарушении публикуется только безопасная причина отказа без содержимого.

## Migration Plan

Срез вводит дополнительную проверку, драйвер и инструкцию. Миграции продукта остаются из PR 2. Вводятся отдельные положительный и отрицательный прогоны CI и доказательство Windows на точном SHA кандидата. Если проверка или инструкция нуждаются в откате, откатываются изменения этих артефактов. Пользовательские тома и ревизии БД сохраняются. Для негативного проекта повтор вместо ремонта использует новый пустой проект.

## Risks / Trade-offs

| Риск | Мера |
| --- | --- |
| Холодная сборка, нестабильный pull или загруженный runner | Раздельные измерения checkout, сборки, старта и health. Классификация сбоя и ограниченное время job. Приёмочный результат учитывает фактический прогон. |
| Установленный Docker Desktop выключен или запущен без Linux-контейнеров | Уведомление после успешного Linux CI, подтверждение готовности от пользователя и preflight. До фактического прогона фиксируется `NOT VERIFIED`. |
| Инъекция или остановка направлена на чужой проект | Явный локальный контекст, свежие уникальные имена и проверка labels и ID. Отказ до любой операции изменения при конфликте. |
| Артефакт потерян, устарел или содержит секрет | Сверка SHA и обязательных полей, публикация очищенных доказательств, срок хранения Linux 30 дней, локальная копия Windows и ссылка в Issue. При изменениях, влияющих на результат, затронутые проверки повторяются. |
| В CI повторяется часть уже принятых интеграционных проверок | Сквозной набор ограничен одним жизненным циклом и одним негативным запуском. Детали PostgreSQL остаются в Backend CI. |

## Open Questions

- Время Windows-прогона определяется после первого успешного Linux CI на SHA кандидата, когда пользователь подтвердит готовность Docker Desktop. Конкретное место публикации очищенного отчёта можно выбрать после прогона из двух согласованных вариантов.
