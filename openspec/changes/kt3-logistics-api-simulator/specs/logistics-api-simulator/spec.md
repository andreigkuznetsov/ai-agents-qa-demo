# Logistics API Simulator

## Purpose

Локальный симулятор воспроизводимо проверяет заказы и регистрирует обращения о переносе доставки в границах авторизованного тестового запуска.

## ADDED Requirements

### Requirement: AC-LAS-001 Версионированные fixtures и изоляция запусков

Симулятор SHALL подготавливать синтетические данные заданной версии для отдельного `run_id` и клиента. Повторная инициализация SHALL допускаться только при совпадении версии и контрольной суммы фактического содержимого fixture. При повторе и отказе SHALL сохраняться доменное состояние всех запусков. Контракт `runs` сохраняется. Срез PR 1, регрессия обращений в PR 3. Ссылки REQ-009, REQ-018, NFR-002, DEC-03, DEC-07, S01–S06.

#### Scenario: SC-LAS-001 Воспроизводимая инициализация заданной версии

- **GIVEN** тестовая инфраструктура подготавливает два разных запуска из одной явно указанной версии синтетического набора
- **WHEN** она инициализирует оба запуска
- **THEN** начальные доменные значения и бизнес-идентификаторы совпадают для этой версии после исключения назначенных запуском идентификаторов и служебных времён
- **AND** допустимые даты одинаковы независимо от текущей системной даты, в номинальных fixtures доступна дата `2026-11-26`
- **AND** с PR 3 fixture S04 создаёт предусмотренный открытый case только в нужном запуске и у его владельца

#### Scenario: SC-LAS-002 Одинаковый номер заказа в независимых запусках

- **GIVEN** синтетический номер заказа встречается в двух запусках, которые имеют отдельные авторизованные контексты
- **WHEN** тест читает данные первого запуска и после появления записи обращений создаёт case только в первом запуске
- **THEN** результат относится к первому запуску, а данные второго и его обращения остаются прежними
- **AND** в PR 1 граница проверяется для доступных сущностей, а в PR 3 повторяется с открытыми обращениями

#### Scenario: SC-LAS-003 Повторная инициализация сохраняет состояние

- **GIVEN** запуск инициализирован с известными версией и контрольной суммой всего содержимого fixture, а после инициализации разрешённое состояние могло измениться
- **WHEN** тестовая инфраструктура повторяет инициализацию с той же версией и тем же содержимым
- **THEN** повтор допустим, число записей и последующие изменения сохраняются, данные другого клиента или запуска не очищаются
- **AND** при той же версии и другом содержимом либо при другой версии, даже с той же суммой, инфраструктура возвращает контролируемый внутренний отказ. Версия, контрольная сумма и данные запуска и соседних запусков остаются прежними

### Requirement: AC-LAS-002 Серверная авторизация и закрытое управление тестом

Backend SHALL связывать непрозрачный синтетический токен с `client_id` и `run_id` и применять этот контекст на всех логистических операциях. Идентификаторы из запроса SHALL не повышать полномочия. Управление fixtures, отказами и административные операции SHALL быть недоступны клиенту Logistics Agent и анонимному запросу. Срез PR 1, проверки маршрутов в PR 2–4. Ссылки REQ-007, REQ-008, REQ-009, REQ-018, DEC-03, DEC-06, S06.

#### Scenario: SC-LAS-004 Недействительные полномочия и подмена контекста

- **GIVEN** у тестового клиента есть контекст только для одного запуска и владельца
- **WHEN** сделан запрос без токена, с недействительным токеном или с одним лишь действительным `run_id`
- **THEN** возвращается `401 UNAUTHENTICATED`, доменное состояние не меняется
- **AND** действительный токен с подставленным `client_id` или `run_id` в запросе не даёт доступа к чужим данным

#### Scenario: SC-LAS-005 Клиентские полномочия не дают управлять тестом

- **GIVEN** анонимный вызывающий или клиент с полномочиями Logistics Agent
- **WHEN** он пытается управлять fixtures, настраивать отказы или выполнять административные операции
- **THEN** действие не выполняется, исходные данные и профиль сбоя остаются прежними
- **AND** тестовая инфраструктура может подготовить свой запуск внутренним способом без публикации административного API или передачи средств управления агенту

### Requirement: AC-LAS-003 Чтение заказа и доступных дат

Симулятор SHALL возвращать состояние своего заказа и доступные даты из закреплённой версии fixtures. Разрешение на перенос SHALL быть возможно только для `ACTIVE`. Чужой, отсутствующий и недоступный в другом запуске заказ SHALL иметь один публичный `404`. Срез PR 2. Ссылки REQ-001, REQ-004, REQ-007, REQ-008, DEC-02, DEC-03, DEC-06, DEC-07, S01, S03, S06.

#### Scenario: SC-LAS-006 Владелец видит закреплённые варианты

- **GIVEN** авторизованному клиенту принадлежит `ACTIVE`-заказ с доступной датой `2026-11-26` в номинальном fixture
- **WHEN** клиент читает заказ и его `delivery-options`
- **THEN** получает текущее состояние и дату исходной доставки, а список вариантов содержит закодированную ISO-дату `2026-11-26`
- **AND** чтение сохраняет состояние заказа и обращений

#### Scenario: SC-LAS-007 Заблокированный заказ и пустой список дат различимы

- **GIVEN** у клиента есть `TRANSFER_BLOCKED`-заказ и отдельный `ACTIVE`-заказ без доступных в fixture дат
- **WHEN** он проверяет варианты переноса для обоих
- **THEN** ни у одного заказа нет доступной даты
- **AND** ответ различает запрещённое состояние и отсутствие дат по предложенному контракту `reason_code`

#### Scenario: SC-LAS-008 Заказ вне границ доступа выглядит отсутствующим

- **GIVEN** клиент предъявил действительный токен, а тест различает отсутствующий ID, чужой заказ и заказ вне авторизованного запуска
- **WHEN** он запрашивает каждый заказ или его доступные даты
- **THEN** статус `404 RESOURCE_NOT_FOUND` и публичное тело одинаковы, сведения о владельце, заказе и датах не выдаются
- **AND** внутреннее свидетельство отказа позволяет проверить авторизацию без публикации токена и чужих данных

### Requirement: AC-LAS-004 Создание открытого обращения с проверкой правил

Backend SHALL проверять авторизацию, запуск, принадлежность заказа, состояние `ACTIVE` и допустимость даты при новой операции записи. Допустимый запрос SHALL создавать `DELIVERY_RESCHEDULE` со статусом `OPEN` без изменения исходного заказа. Запрос без `order_id` SHALL быть отклонён. Срез PR 3. Ссылки REQ-002, REQ-003, REQ-004, REQ-007, REQ-008, DEC-01–04, DEC-06, DEC-07, S01–S03, S06.

#### Scenario: SC-LAS-009 Создание для своего активного заказа

- **GIVEN** клиент авторизован, заказ принадлежит ему в текущем запуске, находится в `ACTIVE`, дата доступна и соответствующего case нет
- **WHEN** клиент отправляет допустимый запрос с новым ключом
- **THEN** приходит `201` с одним новым case типа `DELIVERY_RESCHEDULE`, статусом `OPEN`, нужным заказом и запрошенной датой
- **AND** в БД есть один соответствующий case и привязка ключа к результату, исходная дата и состояние заказа сохранены

#### Scenario: SC-LAS-010 Запрещённый статус и недопустимая дата при прямой записи

- **GIVEN** для заблокированного заказа fixture содержит номинальную дату, а для отдельного активного заказа запрошенная дата не входит в доступный набор. В обоих случаях может уже существовать подходящее открытое обращение
- **WHEN** клиент отправляет запрос с новым ключом напрямую, в том числе после изменения допустимости между чтением и записью
- **THEN** для заблокированного заказа возвращается `409 ORDER_TRANSFER_BLOCKED`, а для недопустимой даты активного заказа — `422 DELIVERY_DATE_NOT_ALLOWED`
- **AND** число case, ключи и исходный заказ не меняются

#### Scenario: SC-LAS-011 Отсутствующий номер и запись вне полномочий

- **GIVEN** запрос не содержит `order_id`, либо указывает отсутствующий, чужой или недоступный из другого запуска заказ
- **WHEN** клиент пытается создать обращение
- **THEN** отсутствие обязательного поля даёт `422 VALIDATION_ERROR`, а недоступный объект — единый публичный `404 RESOURCE_NOT_FOUND`
- **AND** при недействительном токене возвращается `401 UNAUTHENTICATED` до проверки ключа. Для корректно сформированного запроса к недоступному заказу ключ не проверяется, даже если такой ключ уже известен
- **AND** case и привязка ключа не создаются ни в данном, ни в другом запуске

### Requirement: AC-LAS-005 Независимые гарантии идемпотентности и уникальности

Симулятор SHALL проверять аутентификацию, формат и доступность заказа до сопоставления ключа и содержимого. Идемпотентность SHALL ограничиваться клиентом, запуском и типом операции. Уникальность `OPEN`-обращения SHALL проверяться независимо по клиенту, запуску, заказу, дате и операции. Case и ключ SHALL сохраняться согласованно при конкуренции и отказе. Срез PR 3. Ссылки REQ-002, REQ-005, REQ-008, REQ-009, DEC-02–04, S01, S04, S05.

#### Scenario: SC-LAS-012 Повтор того же запроса

- **GIVEN** в текущем клиентском контексте уже зафиксирован результат запроса с ключом
- **WHEN** по-прежнему авторизованный клиент повторяет тот же ключ с тем же содержимым, в том числе с изменённым порядком полей или форматированием JSON
- **THEN** возвращается `200` и тот же case, состояние БД сохраняется
- **AND** сравнение в области `(run_id, client_id, operation_type, key)` использует точный строковый `order_id`, действительную дату `YYYY-MM-DD` и `DELIVERY_RESCHEDULE`. Эквивалентное JSON-экранирование также сохраняет равенство. Идентификатор не приводится к числу и его регистр не меняется
- **AND** изменившиеся состояние заказа и допустимость даты не применяются повторно к сохранённому результату

#### Scenario: SC-LAS-013 Ключ использован с другим содержимым

- **GIVEN** ключ уже связан с результатом для определённого заказа и даты в авторизованной области
- **WHEN** тот же клиент в том же запуске повторяет ключ с другим доступным ему заказом или другой датой
- **THEN** возвращается `409 IDEMPOTENCY_KEY_CONFLICT`, первоначальная привязка и case сохраняются, текущая допустимость не пересчитывается

#### Scenario: SC-LAS-014 Независимые ключи и конкурентные запросы не создают дубликат

- **GIVEN** один допустимый запрос может быть отправлен одновременно с одинаковыми или разными ключами
- **WHEN** реальные запросы конкурируют за создание того же открытого бизнес-обращения
- **THEN** создаётся ровно один case, один ответ `201`, остальные успешные ответы `200` с тем же `case_id`
- **AND** успешно принятый новый ключ для существующего case позволяет впоследствии найти этот case по своему ключу
- **AND** новый ключ требует актуальной проверки состояния и даты даже при наличии бизнес-дубликата
- **AND** тот же ключ в другом авторизованном запуске или у другого клиента не связывается с чужим результатом

#### Scenario: SC-LAS-015 Отказ фиксации не оставляет частичное состояние

- **GIVEN** тестовая инфраструктура может контролируемо сорвать операцию до подтверждения записи
- **WHEN** фиксация запроса прерывается до её успешного завершения
- **THEN** новый case и ключ либо отсутствуют вместе, либо для ранее существовавшего case сохраняется исходное состояние без новой частичной привязки
- **AND** последующая допустимая операция в том же запуске может завершиться согласно правилам уникальности

### Requirement: AC-LAS-006 Чтение только своих обращений

Симулятор SHALL предоставлять чтение открытых обращений по доступному заказу и по идентификатору case в авторизованном контексте. При недоступном объекте SHALL применяться тот же публичный отказ, что для отсутствующего. Срез PR 3. Ссылки REQ-005, REQ-007, REQ-009, DEC-01, DEC-03, DEC-06, S04, S06.

#### Scenario: SC-LAS-016 Список и конкретный case ограничены контекстом

- **GIVEN** в разных запусках или у разных владельцев имеются разные OPEN-обращения, а некоторый доступный заказ обращений не имеет
- **WHEN** клиент читает список по заказу и обращение по `case_id`
- **THEN** возвращаются свои обращения, пустой список для своего заказа без case и единый `404` для недоступного заказа или case
- **AND** чтение сохраняет доменное состояние

### Requirement: AC-LAS-007 Авторизованная сверка неизвестного исхода

Симулятор SHALL предоставлять чтение результата по исходному ключу в границах авторизованных клиента, запуска и заказа. Найденный результат, отсутствие подтверждения и недоступность проверки SHALL различаться. Проверка SHALL не писать в доменную БД и не запускать повторный `POST`. Срез PR 4. Ссылки REQ-005, REQ-006, REQ-007, REQ-009, DEC-03–06, S05, S06.

#### Scenario: SC-LAS-017 Результат найден по исходному ключу

- **GIVEN** создание зафиксировано, исходный ответ потерян, а ключ связан с case в текущем разрешённом контексте
- **WHEN** вызывающий делает одну авторизованную сверку по исходному ключу
- **THEN** возвращается `200 FOUND` с тем же подтверждённым case и без дополнительных записей

#### Scenario: SC-LAS-018 Сверка выполнена без подтверждения результата

- **GIVEN** заказ доступен и сверка технически доступна, но подтверждённый результат ещё не виден, в том числе пока первоначальная запись не зафиксирована или её исход остаётся неопределённым
- **WHEN** вызывающий выполняет сверку
- **THEN** возвращается `200 NOT_FOUND`. Этот исход фиксирует отсутствие подтверждения на момент сверки и не доказывает отказ или откат первоначального `POST`
- **AND** ключ другого клиента или запуска не раскрывается, а для недоступного заказа сохраняется единый `404`
- **AND** сверка не создаёт обращения и не инициирует повторный `POST`. Если исходная запись успешно фиксируется позже, существует ровно один case

#### Scenario: SC-LAS-019 Проверка результата недоступна

- **GIVEN** исход операции неизвестен, а источник результата технически недоступен
- **WHEN** вызывающий выполняет сверку в пределах настроенного бюджета
- **THEN** возвращается `503 RESULT_CHECK_UNAVAILABLE`, исход операции остаётся неизвестным, состояние БД не меняется
- **AND** техническая недоступность не выдаётся за `NOT_FOUND` и не инициирует повторный `POST`

### Requirement: AC-LAS-008 Внутренние воспроизводимые сбои и доказательства

Тестовая инфраструктура SHALL воспроизводить отказ до фиксации и потерю ответа после неё, а также недоступность сверки в пределах запуска. Профиль сбоя SHALL быть недоступен агенту и остальным запускам. Будущий QA Orchestrator SHALL иметь возможность использовать ту же внутреннюю границу без изменения бизнес-контрактов. Срез PR 4. Ссылки REQ-006, REQ-009, REQ-018, REQ-019, NFR-002, NFR-005, DEC-05, S05–S06.

#### Scenario: SC-LAS-020 Потеря ответа до и после фиксации

- **GIVEN** два отдельных тестовых запуска используют воспроизводимые профили сбоя до фиксации и после фиксации case и ключа
- **WHEN** тестовый вызывающий теряет ответ на создание и выполняет по одной разрешённой сверке
- **THEN** первый запуск не даёт подтверждённого результата и не имеет новой записи, второй подтверждает ровно один case
- **AND** между исходным запросом и сверкой тест не выполняет автоматический повторный `POST`

#### Scenario: SC-LAS-021 Недоступность сверки изолирована

- **GIVEN** тестовый профиль делает сверку недоступной в одном запуске и другой запуск имеет доступный подтверждённый результат
- **WHEN** оба клиента выполняют сверку в своих контекстах
- **THEN** только первый получает техническую недоступность, второй подтверждает свой результат, оба сохраняют состояние БД

#### Scenario: SC-LAS-022 Тестовое управление не меняет клиентский контракт

- **GIVEN** профиль сбоя задан внутренним тестовым способом для известной версии fixture, запуска и операции
- **WHEN** тест воспроизводит профиль, а клиент пытается включить его аргументами публичного запроса
- **THEN** внутренняя репетиция даёт тот же наблюдаемый исход, клиентская попытка не меняет профиль и других запусков не касается
- **AND** безопасные доказательства фиксируют фазу сбоя и результат сверки без секретов, а клиентский контракт сохраняет тот же набор операций и ответов
