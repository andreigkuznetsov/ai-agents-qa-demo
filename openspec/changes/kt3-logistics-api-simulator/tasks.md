## Приёмка и SDD

- Для каждого PR указать список его задач, фактическое покрытие и зависимые проверки. Планируемые проверки последующих срезов записывать как ожидающие. Приёмка каждого PR требует применимых CI, связи через GitHub Development, независимого ревью полного diff на точном HEAD и решения пользователя. Отмечать задачи только после получения указанного доказательства.
- Манифест каждого будущего PR связывает только реально проверяемые задачи со сценариями через путь к утверждённой дельте и идентификаторы AC/SC. Для каждой связи указывать существующий селектор теста или принятую ручную запись. Scope манифеста перечисляет реальные изменённые пути. Структурная проверка checker дополняется журналами запуска тестов.
- До открытия первого продуктового PR согласовать, как утверждённые planning-артефакты попадут в его базу. Текущий checker требует доказательства для всех сценариев изменившейся дельты, если она впервые добавлена в diff PR 1. Рекомендуемый вариант для отдельного решения — принять версионированную planning-базу до продуктового среза через согласованный процесс SDD, который явно отличает проверку планов от доказательств реализации. Существующий режим `tooling` для новой дельты недоступен. Манифесты ранних срезов не могут заявлять успешное покрытие поздней функциональности.
- Эксплуатационные численные дедлайны требуют отдельного утверждения после замеров 3.17 и 4.7. Проверки используют явные тестовые значения из согласованных границ и сохраняют бюджеты КТ2. Формат внутреннего транспорта fixtures и профилей уточняется в границах Design.
- Границы приёмки — Logistics API Simulator, синтетические данные и шесть утверждённых маршрутов. Материалы КТ1, действующие спецификации КТ2, четыре поля `runs`, неизменность расписания доставки и OPEN-only сохраняются. Синхронизация и архивирование изменения требуют результатов всех четырёх PR и отдельного решения.
