# Tasks — КТ4 Logistics Agent

Change-id `kt4-logistics-agent`. Стадия Tasks ожидает утверждения. [Issue №25 и утверждение Design](https://github.com/andreigkuznetsov/ai-agents-qa-demo/issues/25#issuecomment-7143134159) · [Proposal](proposal.md) · [Requirements](specs/logistics-agent/spec.md) · [Design](design.md) · [Решения КТ4](../../../docs/development/kt4-business-decisions.md)

План содержит 30 задач на три продуктовых PR. Основная целевая среда — Linux VDS с Docker Compose. Windows используется для разработки и проверки переносимости блокировок и защиты путей. SQLite хранит приватный долговечный журнал одного хоста. Бизнес-данные и независимые доказательства остаются в PostgreSQL КТ3.

## Профиль хранения и ограничения исполнения

- Кандидат для проверки — отдельный долговечный bind mount заранее созданного приватного каталога вне checkout и синхронизируемых областей. Использовать длинный синтаксис Compose с `type: bind` и `bind.create_host_path: false` в изолированной конфигурации запуска или теста. До вызова Compose доверенный контур на хосте отдельно проверяет наличие и принадлежность источника. Действующие Compose, Dockerfile, CI, миграции, контракты и роли КТ2–КТ3 сохраняются. SQLite не размещается в слое контейнера, `tmpfs`, каталоге PostgreSQL или на общем сетевом томе. Источник и дочерние каталоги контролирует доверенный оператор. [Docker bind mounts](https://docs.docker.com/engine/storage/bind-mounts/) · [Compose volumes](https://docs.docker.com/reference/compose-file/container-spec/#long-syntax)
- До допуска требуется подтвердить ФС и путь на хосте, а также фактический mount, эффективные UID/GID и mapping при user namespaces или rootless внутри контейнера. Текущий runtime-образ задаёт `10001:10001`. Проверяется, каким ID реально принадлежит каталог на хосте и как он виден контейнеру. Каталог должен соответствовать `0700`, SQLite, служебные и lock-файлы — `0600`. Не исправлять права запуском от root, ослаблением доступа или автоматическим `chmod/chown`. [Runtime Dockerfile](../../../backend/Dockerfile) · [Docker user namespaces](https://docs.docker.com/engine/security/userns-remap/)
- Сверка путей делается с обеих сторон bind mount. Допустимы локальные ФС из Design, закрытые пути и согласованное владение. Ошибка проверки, сетевой, временный или неподдерживаемый том, подмена сегмента и несовместимый UID дают отказ до внешних вызовов. Текущий Linux-профиль проверяется фактически. Windows Docker Desktop mount не подменяет проверку нативных Windows `LockFileEx` и DACL.
- Для испытания пересоздания использовать один изолированный Compose-проект и один выделенный mount, два сравниваемых ID контейнера и один `operation_id`. После маркера расходования заменить только тестовый контейнер и заново прочитать тот же журнал и маркер. Подтвердить сохранность каталога, SQLite-состояния и отсутствие повторного POST. Хостовый путь и значения ключей не публиковать. Тестовый каталог, тома и чужие ресурсы не удалять.
- В требованиях к постоянному mount и утверждённом Design не выявлено конструктивного противоречия для этого профиля. Фактическая совместимость VDS пока не проверена. Если Docker отображает хранилище как сетевую или неподдерживаемую ФС либо проверка идентичности каталога и UID не проходит, зафиксировать конкретное расхождение. Кандидат на корректировку — отдельный предварительно подготовленный приватный локальный bind mount с корректным UID mapping. Если такой mount несовместим с целевой средой, остановить допуск и отдельно согласовать изменение Design. Ослабление проверок не входит в план.

## Зависимости, приёмка и открытые решения

- Последовательность срезов — принятый PR 1 перед PR 2, принятый PR 2 перед PR 3. Зависимости отдельных задач указаны в строках. PR 1 требует работающих контрактов КТ3. PR 2 требует изолированных настоящих Simulator и PostgreSQL, двухпроцессных проверок на Linux и Windows, наблюдаемого HTTP и независимого DB evidence. PR 3 требует целевого Linux VDS с проверенным mount и соответствующим доступом к разрешённому API. Недоступные прогоны отражаются фактически.
- PR 1 доказывает контракты всех шести инструментов, классификацию и разграничение контекста. PR 2 доказывает S01–S06 со сценарным портом, отсутствие побочной записи, обработку отказов и безопасность журнала. PR 3 доказывает один реальный live S01 с независимо найденным обращением. Сценарный S01 и оракулы БД не доказывают фактическое поведение реального LLM. Стабильность реальной модели к prompt injection остаётся предметом отдельной проверки.
- Для каждого продуктового PR требуются точный scope, фактические тесты и evidence для своего среза, привязка GitHub Development, независимое ревью проверенного SHA и итоговые CI. Системный аудит проводится по правилам проекта. Изменения управления состояниями и долговечности в PR 2 требуют досрочного аудита, до приёмки среза. Перед релизом проверяется точный release commit. [Процесс SDD](../../../docs/development/sdd-process.md) · [Процесс ревью](../../../docs/development/review-process.md) · [Процесс аудита](../../../docs/development/audit-process.md)
- DEC-08, конкретная модель и провайдер, разрешённый хост и доступ к API, профиль UID/тома на VDS, тестовые параметры write/result и бюджеты live остаются открытыми. A/B остаются вариантами. Если разрешённый live недоступен, фиксируется BLOCKED_PRECONDITION, живой сценарий остаётся неприёмочным.
- Следующие ворота — утверждение Tasks. Публикация planning baseline требует отдельного разрешения. Строгая валидация структуры и локальная проверка трассировки подтверждают качество плана. Продуктовые задачи закрываются только по фактическим доказательствам.
