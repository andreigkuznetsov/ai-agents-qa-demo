# Logistics Agent

## Purpose

Обеспечить управляемое исполнение запросов на перенос доставки в синтетическом стенде КТ3. Зафиксировать наблюдаемые условия безопасности, последовательности и приёмки Logistics Agent на КТ4.

## ADDED Requirements

### Requirement: AC-LAG-001 Типизированные контракты шести инструментов

HTTP-адаптер SHALL предоставлять только шесть инструментов в таблице контрактов, принимать ровно разрешённые типизированные аргументы и выдавать только разрешённые поля. Путь строится из проверенного ID как одного сегмента. Поставщик модели не задаёт HTTP-метод, базовый адрес, произвольные заголовки или параметры.

#### Scenario: SC-LAG-001 Контрактные вызовы успешны

- **GIVEN** адаптер получает корректные аргументы для каждого из шести инструментов
- **WHEN** соответствующий маршрут КТ3 отвечает утверждённым телом
- **THEN** фактический метод, путь, заголовки, тело и тип результата совпадают с таблицей, включая пустой список и обе формы сверки

Обозначение case соответствует утверждённым полям `case_id`, `order_id`, `requested_date`, `operation_type`, `status`. Даты передаются в ISO `YYYY-MM-DD`, `case_id` — UUID. `order_id` — непустой идентификатор заказа из контекста запроса. Тип операции записи `DELIVERY_RESCHEDULE`, статус case `OPEN`.

| Инструмент | Аргументы исполнителя | HTTP и типизированный результат |
| --- | --- | --- |
| `get_order` | `order_id` | GET `/orders/{order_id}`, 200 с `order_id`, `status`, `scheduled_delivery_date` |
| `get_delivery_options` | `order_id` | GET `/orders/{order_id}/delivery-options`, 200 с `order_id`, `eligible`, `reason_code`, `dates` |
| `get_order_cases` | `order_id` | GET `/orders/{order_id}/cases`, 200 с `cases` |
| `get_case` | `case_id` | GET `/cases/{case_id}`, 200 с case |
| `create_case` | `order_id`, `requested_date` | POST `/cases`, 201 с новым case либо 200 с существующим, исходный ключ добавляет сервер |
| `check_case_result` | Только доверенный контекст операции, без аргументов от модели | GET `/orders/{order_id}/case-result` с исходным ключом, 200 `FOUND` с case или `NOT_FOUND` с `case=null`, 503 при недоступности |

Bearer для всех операций берётся из серверного контекста. Оба маршрута с ключом сохраняют формат КТ3, включая ограничение 512 байт UTF-8. Для POST тело включает `order_id`, `requested_date` и фиксированный `operation_type`. Публичные ошибки получают классификацию из `error.code`. Исходные контракты подчиняются [спецификации КТ3](../../../../specs/logistics-api-simulator/spec.md).

#### Scenario: SC-LAG-002 Недопустимая форма входа

- **GIVEN** в аргументах есть неверный тип, лишнее поле, пустой ID или попытка изменить путь
- **WHEN** адаптер проверяет аргументы
- **THEN** HTTP-запрос не выполняется, причина отказа доступна в безопасной классификации

### Requirement: AC-LAG-002 Серверный контекст и границы полномочий

Адаптер SHALL использовать Bearer из доверенного серверного контекста текущих клиента и запуска на всех шести маршрутах. Агенту доступны только клиентские операции КТ3. Синтетическая роль подготовки фикстур и управление отказами остаются у доверенной тестовой инфраструктуры. Bearer, Idempotency-Key и учётные данные не передаются модели.

#### Scenario: SC-LAG-003 Подмена полномочий отклоняется

- **GIVEN** два клиента или запуска имеют одинаковый order_id, а вход или модель подставляет run_id, client_id либо Authorization
- **WHEN** выполняется чтение или предлагается запись
- **THEN** фактический Bearer остаётся привязанным к текущему контексту, подставленные поля не влияют на полномочия, данные чужого контекста и секреты не выдаются

Отдельный вариант проверки использует разные синтетические маркеры для Bearer, Idempotency-Key и учётных данных. При обращении к модели ни один маркер не встречается во входе LLM-адаптера или в фактическом исходящем payload для модели. Проверка EventSink и итогового отчёта не заменяет проверку этого payload.

#### Scenario: SC-LAG-004 Нет административного маршрута

- **GIVEN** вызов нацелен на загрузку fixtures, fault profile, смену роли, SQL или произвольный URL
- **WHEN** предложение попадает на границу адаптера
- **THEN** вызов отклонён до HTTP, административные полномочия агенту не доступны

### Requirement: AC-LAG-003 Намерение и однозначная бизнес-дата

Executor SHALL различать информационный запрос и явную просьбу о создании обращения. Для записи требуются факты из высказывания пользователя или ранее однозначно подтверждённого состояния того же серверного контекста. Дата без года требует доверенного reference_year и единственного совпадения дня и месяца среди доступных дат, относящегося к reference_year. Системное время не определяет дату.

#### Scenario: SC-LAG-005 Информация и неполные данные

- **GIVEN** пользователь спрашивает о возможности, не указал заказ, указал один неполный или неоднозначный номер либо указал несколько заказов
- **WHEN** модель предлагает запись или предполагает номер
- **THEN** информационный запрос ограничивается чтениями, а при недостающих или неоднозначных данных агент запрашивает уточнение, не угадывает и не перебирает ID и не делает POST

#### Scenario: SC-LAG-006 Явная просьба о переносе

- **GIVEN** клиент просит перенести свой конкретный заказ на допустимую полную дату либо дату без года с доверенным reference_year и единственным совпадением
- **WHEN** сервер проверяет заказ и условия
- **THEN** дополнительное подтверждение не требуется, запись допускается через обычные ворота

#### Scenario: SC-LAG-007 Неоднозначные и недоступные даты

- **GIVEN** дата относительная, есть несколько вариантов, отсутствует доверенный год для частичной даты либо полная дата недопустима
- **WHEN** сервер сопоставляет данные пользователя с вариантами API
- **THEN** первые три случая ведут к уточнению, при недопустимой полной дате агент объясняет отказ и может показать варианты, во всех случаях POST отсутствует

### Requirement: AC-LAG-004 Последовательные переходы и разрешение записи

Executor SHALL владеть переходами операции от намерения через проверку заказа, дат и дубликата к разрешению записи, POST и подтверждённому, отклонённому или неопределённому исходу. Чтение, уточнение и обнаружение дубликата допускают раннее завершение. Перед подтверждением новых записей требуется валидное свидетельство API. Для подтверждённого ответа указывается создание или наличие обращения, исходная доставка не объявляется перенесённой.

#### Scenario: SC-LAG-008 Запись только после всех ворот

- **GIVEN** получена явная однозначная просьба и активный доступный заказ без дубликата
- **WHEN** модель предлагает нужные инструменты или пытается вызвать POST преждевременно
- **THEN** POST допускается только после валидных результатов заказа, дат и поиска дубликата, успешное подтверждение соответствует ответу API

#### Scenario: SC-LAG-009 Дубликат и запрет записи

- **GIVEN** найден подходящий OPEN, заказ заблокирован или нет допустимых дат
- **WHEN** исполняется проверка условий
- **THEN** существующее обращение возвращается без POST в разрешённом сценарии, причины блокировки и отсутствия дат различаются, при отказе записей нет

### Requirement: AC-LAG-005 Долговечное расходование разрешения и восстановление

Сервер SHALL владеть идентичностью операции и ключом идемпотентности. Стабильный ID связывает повторную доставку той же операции с её состоянием. До передачи POST транспорту разрешение расходуется долговечно и однократно. При ошибке фиксации разрешения POST запрещён. Незавершённая операция после сбоя восстанавливается безопасно, без автоматической повторной записи, генерации нового ключа для повтора или вывода об отправке либо commit из одного маркера.

#### Scenario: SC-LAG-010 Граница до транспорта

- **GIVEN** разрешение долговечно израсходовано, но процесс остановлен до вызова транспорта
- **WHEN** по тому же ID восстанавливается состояние
- **THEN** POST не выполняется, статус допускает неопределённость и не утверждает отправку либо фиксацию

Отдельный вариант проверяет ошибку долговечной фиксации. При попытке сохранить отметку хранилище возвращает ошибку. Транспорт POST не вызывается, расходование разрешения не подтверждается, автоматического повтора записи нет. Ошибка отражается безопасным техническим свидетельством без секретов и внутренних подробностей. Успешный результат обращения не заявляется.

#### Scenario: SC-LAG-011 Граница после транспорта

- **GIVEN** процесс прекращён после передачи POST, но до надёжной фиксации подтверждения результата
- **WHEN** тот же запуск доставлен повторно, включая конкурирующую доставку
- **THEN** разрешение на запись повторно не выдаётся, новый ключ для повторного POST не создаётся, итог без надёжного подтверждения остаётся UNKNOWN, в БД максимум один case

### Requirement: AC-LAG-006 Классификация HTTP и транспортных результатов

Адаптер SHALL различать корректные успехи 200/201, публичные отказы 401/404/409/422 и 503 сверки. Подтверждение допустимо только для ожидаемого статуса и валидного типизированного тела в контексте операции. Сбой транспорта или неполный ответ после передачи POST означает возможную запись. Диагностика и ответы не раскрывают внутренние исключения.

#### Scenario: SC-LAG-012 Успех и нормативные отказы

- **GIVEN** КТ3 возвращает 200, 201, 401 UNAUTHENTICATED, 404 RESOURCE_NOT_FOUND, 409 ORDER_TRANSFER_BLOCKED или IDEMPOTENCY_KEY_CONFLICT, 422 DELIVERY_DATE_NOT_ALLOWED или VALIDATION_ERROR, либо 503 RESULT_CHECK_UNAVAILABLE для сверки
- **WHEN** адаптер классифицирует ответы
- **THEN** публичные коды различимы внутри, 404 имеет одинаковую публичную семантику, ни один отказ не выдаёт подтверждение создания или чужие сведения

#### Scenario: SC-LAG-013 Ошибки вне нормативного ответа

- **GIVEN** транспорт завершился ошибкой, тело повреждено или статус неожиданен
- **WHEN** адаптер получает результат чтения или переданного POST
- **THEN** для чтения возвращается контролируемый технический исход, для POST с возможной доставкой сохраняется неопределённость, исключения и сырые ответы не уходят модели или в отчёт

### Requirement: AC-LAG-007 Одна безопасная сверка

Executor SHALL использовать исходный Idempotency-Key и тот же авторизованный контекст для максимум одной сверки после возможной отправки POST с неизвестным исходом. Сверка не запускает повтор записи. Резерв на сверку проверяется до допуска POST.

#### Scenario: SC-LAG-014 FOUND после потери ответа

- **GIVEN** ответ POST потерян после фиксации
- **WHEN** executor выполняет сверку
- **THEN** FOUND подтверждает существующий case, в БД одна запись и POST был один

#### Scenario: SC-LAG-015 Нет подтверждения результата

- **GIVEN** POST не зафиксирован, ещё не виден, сверка недоступна или срок истёк
- **WHEN** executor получает NOT_FOUND, 503, отказ доступа или тайм-аут сверки
- **THEN** сообщается UNKNOWN, NOT_FOUND не считается доказанным отказом первоначальной записи, повторный POST и вторая сверка отсутствуют

### Requirement: AC-LAG-008 Недоверенные данные и предложения модели

Executor SHALL проверять каждый инструмент по текущему состоянию, схеме, контексту и лимитам. Текст из инструментов и предложения модели не могут расширить полномочия, выдать секрет или создать разрешение на запись. Пакет с несколькими вызовами не исполняется частично.

#### Scenario: SC-LAG-016 Недоверенный вывод и неверный вызов

- **GIVEN** в выдаче инструмента есть внедрённый текст либо модель предлагает чужой ID, запрещённый инструмент или несколько вызовов
- **WHEN** executor обрабатывает предложение
- **THEN** внедрённые данные не влияют на правила, запрещённые предложения отклоняются, пакет вызовов отвергается целиком, запись и раскрытие отсутствуют

### Requirement: AC-LAG-009 Пределы вызовов, времени и расходов

Executor SHALL ограничивать операцию шестью обращениями к модели, шестью попытками инструментов включая отклонённые предложения, одним POST и одной сверкой. Допустимы только явные временные и денежные лимиты для live. Исполнение учитывает совокупный расход, консервативную оценку перед вызовом и остаток времени на безопасное завершение. Скрытые автоматические повторы отключены.

#### Scenario: SC-LAG-017 Исчерпание счётчиков

- **GIVEN** одиночные, параллельные и отклонённые предложения расходуют лимит
- **WHEN** в независимом варианте достигнут один предел, остальные счётчики ниже своих пределов и запрашивается ещё один вызов этого вида
- **THEN** дополнительный вызов отклоняется и проверяется его отсутствие на соответствующей внешней границе

| Граничный вариант | Проверка отсутствия внешнего вызова |
| --- | --- |
| Седьмое обращение к модели | LLM-адаптер не вызывается седьмой раз. |
| Седьмая попытка инструмента | HTTP-запрос седьмого инструмента не отправляется. |
| Второй POST | Второй POST не передаётся HTTP-транспорту. |
| Вторая сверка | Второй GET к маршруту сверки не передаётся HTTP-транспорту. |

#### Scenario: SC-LAG-018 Недостаток времени или бюджета

- **GIVEN** лимит истёк, верхняя оценка следующего вызова превышает остаток или резерв сверки отсутствует
- **WHEN** планируется модельный вызов либо POST
- **THEN** дополнительный расход или новая запись не допускаются, неопределённая ранее начатая операция остаётся UNKNOWN

### Requirement: AC-LAG-010 Безопасные события и полная история live

EventSink SHALL фиксировать безопасную корреляцию, версию исполнения и итог каждой допущенной или заблокированной live-попытки. usage, latency и стоимость отражаются с указанием источника и неизвестных значений. Сырые пользовательские данные, токены доступа, ключи идемпотентности, DSN, сырые тела, скрытые рассуждения и персональные данные исключены.

#### Scenario: SC-LAG-019 Корреляция и проверка на утечки

- **GIVEN** сценарный и live-режимы создают события, а синтетические маркеры переданы во входах и ответах
- **WHEN** собирается отчёт
- **THEN** доступны неприватные ID, SHA, модель, промпт и fixture, переходы, результат, счётчики и ссылки на доказательства, запрещённых значений в артефакте нет

#### Scenario: SC-LAG-020 Серия сохраняет неудачные попытки

- **GIVEN** попытки успешны, отклонены, прерваны или имеют неопределённый итог
- **WHEN** проверяется безопасный отчёт серии
- **THEN** для каждой попытки есть отдельная запись, PASS опирается на полный набор доказательств, FAIL фиксирует наблюдаемое нарушение критерия, INCONCLUSIVE означает недостаточные доказательства, BLOCKED_PRECONDITION означает отсутствие допуска, неизвестный расход отмечен

### Requirement: AC-LAG-011 Операторский допуск и синтетический стенд

Live SHALL запускаться локальным CLI доверенного оператора, с отдельным синтетическим run_id на каждую live-попытку, закреплённым fixture и серверным Bearer-контекстом. До PR 3 пользователь отдельно утверждает DEC-08, доступную разрешённую среду, провайдера, версию модели и бюджеты. Обход территориальных ограничений запрещён. Публичный API управления не предоставляется.

#### Scenario: SC-LAG-021 Preflight блокирует запуск

- **GIVEN** нет подтверждённого разрешённого доступа, не согласована модель или бюджет либо стенд не готов
- **WHEN** оператор инициирует приёмку
- **THEN** записывается BLOCKED_PRECONDITION, платная модель и запись обращения не запускаются

#### Scenario: SC-LAG-022 Доверенная подготовка изолирована

- **GIVEN** разрешённый провайдер, модель, бюджеты и исправный стенд прошли preflight
- **WHEN** допущена live-попытка
- **THEN** она получает отдельный синтетический запуск и версионированный fixture, контекст клиента привязан сервером, публичное управление и доступ агента к загрузчику отсутствуют. Необходимые параметры write и result API заданы явно для тестового контура в рамках согласованного допуска

### Requirement: AC-LAG-012 Раздельные доказательства сценарного и live-исполнения

Приёмка SHALL различать сценарные проверки S01–S06, обязательный фактический S01 с выбранной реальной моделью и последующие программы КТ5, КТ6 и КТ9. Сценарный адаптер подтверждает серверное исполнение. Результат live S01 относится к проверенной версии модели и попытке.

#### Scenario: SC-LAG-023 Детерминированная приёмка

- **GIVEN** сценарный адаптер задаёт выходы модели для S01–S06
- **WHEN** прогон проверяет вызовы, публичный итог и побочные эффекты
- **THEN** доказательства помечены как сценарные, платный вызов не требуется, стойкость реальной модели к prompt injection не заявляется

#### Scenario: SC-LAG-024 Фактический S01

- **GIVEN** среда допущена и реальная модель получила синтетическую просьбу S01
- **WHEN** модель выбирает инструменты, executor проводит операцию и наблюдатель независимо читает БД
- **THEN** PASS требует наблюдавшейся последовательности и одного ожидаемого OPEN case с правильным контекстом и датой, исходная дата сохранена, итог сообщает о создании обращения. Заблокированный, неудачный или неподтверждённый прогон не закрывает live-критерий
