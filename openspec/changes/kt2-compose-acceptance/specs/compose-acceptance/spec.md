# Приёмка локального Compose-стенда

## Purpose

Воспроизводимый прогон связывает инфраструктурные контракты, обычные действия оператора и доказательства приёмки локального стенда. Инструкция позволяет повторить этот путь на поддерживаемых платформах.

## ADDED Requirements

### Requirement: AC-CAF-001 Воспроизводимый чистый запуск в CI

CI SHALL выполнять полный Compose smoke на точном SHA проверяемого изменения из чистого checkout и отдельного проекта с пустым томом БД. Прогон SHALL использовать поддерживаемый путь запуска из инструкции и сохранить версию окружения, результат миграции, health, сетевые привязки и итог каждого шага. Источники REQ-019, NFR-001, NFR-005.

#### Scenario: SC-CAF-001 Чистый запуск стенда

- **GIVEN** чистый checkout точного SHA, отдельный Compose-проект без запущенных сервисов и пустой том PostgreSQL
- **WHEN** CI задаёт синтетические учётные данные, собирает образ из checkout по закреплённым зависимостям и запускает стенд по инструкции
- **THEN** ожидаемая упакованная ревизия установлена, одноразовый мигратор завершился с кодом `0` до запуска API, а все три health-маршрута отвечают по принятому контракту в бюджетах PR 2
- **AND** доступ к HTTP с хоста подтверждён на loopback, порт PostgreSQL на хосте не опубликован, а внутренний доступ к БД подтверждён
- **AND** доказательства связывают SHA, использованные версии, состояние сервисов, ревизию и результаты HTTP с этим прогоном. Базовые контракты описаны в AC-PG-001, AC-PG-003 и AC-PG-004

### Requirement: AC-CAF-002 Сохранность данных при штатном цикле остановки

Сквозной прогон SHALL проверить запись с синтетическим UUID через штатный слой хранения, остановить стенд с сохранением тома и после запуска того же проекта подтвердить сохранность записи. Источники REQ-009 в технической части и NFR-001.

#### Scenario: SC-CAF-002 Повторный запуск после безопасной остановки

- **GIVEN** стенд, запущенный по SC-CAF-001, и сохранённая через хранилище синтетическая запись с известным `run_id`
- **WHEN** выполняется обычная остановка и повторный запуск того же проекта с тем же томом и образом
- **THEN** при остановке API и БД прекращают работу, том сохраняется, повторная миграция завершается успешно и API снова готов
- **AND** слой хранения возвращает ровно одну запись по тому же UUID с теми же четырьмя значениями, а история прогона показывает один и тот же том и ожидаемую ревизию. Базовые контракты описаны в SC-PG-003 и SC-RUN-003

### Requirement: AC-CAF-003 Наблюдаемые отказы и восстановление Compose-стенда

CI SHALL проверять потерю и восстановление готовности работающего стенда и диагностируемый отказ миграции при чистом старте отдельного тестового проекта. Обязательная проверка SHALL завершаться с ошибкой при нарушении ожидаемого результата, при тайм-ауте проверки или отсутствии обязательного доказательства. Источники REQ-019, NFR-002, NFR-005.

#### Scenario: SC-CAF-003 Прерывание и восстановление доступа к PostgreSQL

- **GIVEN** Compose-стенд с готовым API и PostgreSQL на ожидаемой ревизии
- **WHEN** БД штатно останавливают, оставляя API работающим, а затем возвращают ту же БД
- **THEN** при отказе `/health/live` отвечает `200 {"status":"ok"}`, а `/health/ready` и `/healthz` отвечают `503 {"status":"unavailable"}` в согласованном бюджете
- **AND** после восстановления оба readiness-маршрута возвращают `200 {"status":"ok"}` без перезапуска API. Журнал фиксирует последовательность ответов и идентичность экземпляра API. Контракты отказа и восстановления описаны в SC-PG-004 и SC-PG-005

#### Scenario: SC-CAF-004 Управляемый отказ миграции

- **GIVEN** отдельный изолированный Compose-проект с пустым томом и контролируемой причиной отказа на стадии миграции
- **WHEN** CI запускает поддерживаемый путь запуска
- **THEN** стадия миграции завершается ожидаемым ненулевым кодом, API не запускается, а в доказательства попадают код и безопасная диагностическая категория
- **AND** успешный результат этого негативного сценария требует подтверждения всех ожидаемых признаков. Доказательства не раскрывают пароли, DSN, токены или персональные данные. Базовый контракт чистого старта описан в SC-PG-002

### Requirement: AC-CAF-004 Поддерживаемая инструкция запуска и диагностики

Инструкция SHALL содержать воспроизводимые действия для Windows с Docker Desktop и Linux с Docker Compose. Для каждой платформы приёмка SHALL требовать фактическое подтверждение прогона опубликованных команд. Источники NFR-001, NFR-002, NFR-005.

#### Scenario: SC-CAF-005 Проверка инструкции на двух платформах

- **GIVEN** чистый checkout кандидата, Windows с работающим Docker Desktop и Linux с работающим Docker Engine и Compose
- **WHEN** по инструкции для каждой платформы проверяют инструменты и окружение, задают отдельные локальные credentials, собирают и запускают проект, проверяют три health-маршрута, состояние мигратора, останавливают и повторно запускают стенд
- **THEN** результаты совпадают с указанными ожидаемыми состояниями, том переживает остановку, а запись доказательств содержит платформу, версии, SHA, команды и фактический результат
- **AND** инструкция описывает проверку контекста и проекта, ожидаемые состояния, ограниченное ожидание, диагностику ошибок конфигурации, занятых портов и отказов БД или мигратора. Недоступная платформа отражается как неподтверждённая до решения пользователя

### Requirement: AC-CAF-005 Защита локального состояния и доказательств

Поддерживаемый путь эксплуатации SHALL ограничивать действия изолированным локальным проектом, сохранять пользовательские тома при обычной остановке и исключать секреты из Git и публикуемых доказательств. Удаление томов требует отдельного согласования. Источники NFR-001 и NFR-002.

#### Scenario: SC-CAF-006 Безопасные действия оператора и отчётность

- **GIVEN** инструкция и результаты сквозного прогона с синтетическими данными
- **WHEN** проверяющий сверяет команды остановки и диагностики, предупреждения, лог и отчёт CI
- **THEN** обычная остановка сохраняет том и не требует доступа к production, инструкция содержит явное предупреждение о потере данных при удалении тома и правило отдельного согласования, а команды удаления томов в штатном пути отсутствуют
- **AND** отчёт содержит только нужные поля и фактические результаты. Пропущенный сценарий или отсутствие доказательства отмечается явно, секреты не публикуются
