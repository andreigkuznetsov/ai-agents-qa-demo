Из другого соединения подтвердить отсутствие новых таблиц, ревизии и прав после rollback. Сохраняются схема и роли, созданные bootstrap. После его явно подтверждённой остановки внедрить сбой и проверить сохранность прежнего head и записи, отсутствие старта нового API и отсутствие автоматического запуска старого. - [x] 1.4 Добавить отдельные тесты полномочий роли API. Связь: AC-PG-001 / SC-PG-001, AC-PG-002 / SC-PG-003, AC-RUN-001 / SC-RUN-001. После первой и повторной миграции проверить подлинное подключение как `qa_api`, чтение `alembic_version`, вставку и чтение `runs`. В отдельных транзакциях проверить `42501` для DDL в `qa` и `public`, `CREATE TEMP TABLE`, `CREATE SCHEMA`, `ALTER/DROP` тестовых объектов, `DELETE`, записи в `alembic_version` и `SET ROLE qa_migrate`. После первой и повторной миграции проверить эффективные права через has_database_privilege и has_schema_privilege, включая права от PUBLIC и членства: CONNECT к целевой БД и USAGE на qa разрешены, CREATE и TEMPORARY на БД и CREATE в qa/public запрещены. Готово, когда проверка каталога и реальные попытки SQL согласуются, вставка и чтение проходят, запрещённые операции отклоняются, данные и схема целы.

Проверить четыре поля, UTC, чтение по двум UUID, отказ на дубле без перезаписи и отсутствие обращения к `runs` при несовместимой ревизии. Готово, когда трасса теста подтверждает одну аренду соединения и одну транзакцию на пару «проверка ревизии → операция», а результат вставки виден из независимого соединения после commit.
- [x] 1.6 Добавить проверки отмены операций хранения. Связь: AC-RUN-001 / SC-RUN-001, SC-RUN-002 и AC-PG-003 / SC-PG-008. Отменить операцию до commit и отдельно смоделировать неопределённый исход во время commit. Готово, когда отмена не подавляется, транзакция до commit не оставляет строки, сомнительное соединение не возвращается как исправное, неопределённый исход проверяется по первоначальному UUID без автоматической повторной вставки, а следующая операция проходит.

Готово, когда оба readiness-маршрута возвращают один и тот же статус и JSON, liveness остаётся `200` без доступа к БД, а возврат PostgreSQL с ожидаемым head восстанавливает `200` без перезапуска API.
- [x] 1.8 Добавить отдельные проверки задержки подключения, задержки SQL, исчерпания пула и отмены readiness. Связь: AC-PG-003 / SC-PG-005, SC-PG-008. Для подключения использовать управляемую задержку до установления нового соединения, для SQL — задержку или блокировку проверочного запроса на уже открытом соединении. Занять два соединения для проверки пула. Проверить отмену единственного ожидающего и отмену одного из двух. Готово, когда ответы при тайм-ауте укладываются в `3 с + 500 мс`, третье соединение не создаётся, отмена одного ожидающего не ломает проверку второго, а минимум после трёх циклов checkout возвращается к исходному значению. Не остаётся накопленных сессий API или `idle in transaction`, следующий readiness и операция с `runs` проходят.
- [x] 1.9 Подготовить локальные проверки сети и сохранности тома Compose. Связь: AC-PG-004 / SC-PG-007, AC-RUN-002 / SC-RUN-003. ## 2. Инфраструктура и миграции

Подготовить `db`, одноразовый `migrate` и `api` с одним образом приложения, именованным томом PostgreSQL, закрытым портом БД и HTTP на loopback. Зависит от 1.1, 1.2 и 1.9. Связь: AC-PG-001 / SC-PG-001, AC-PG-004 / SC-PG-007, AC-RUN-002 / SC-RUN-003. Готово, когда конфигурация Compose проходит проверку, образы собираются, инспекция подтверждает сетевые и дисковые границы.
- [x] 2.2 Реализовать bootstrap ролей и схемы для пустого тома. Разделить credentials, отозвать у PUBLIC CONNECT, CREATE и TEMPORARY в целевой БД и CREATE в qa/public. Вернуть CONNECT только нужным ролям и выдать API USAGE на qa. Исключить членство `qa_api` в роли мигратора. Зависит от 2.1, использует тесты 1.4. Связь: AC-PG-001 / SC-PG-001, SC-PG-002 и AC-RUN-001 / SC-RUN-001. Готово, когда владелец схемы и атрибуты ролей проверяются на свежей БД, а существующий том без ожидаемой конфигурации даёт контролируемый отказ до DDL.
- [x] 2.3 Реализовать начальную ревизию `runs` и управление транзакцией мигратора. Передать Alembic внешнее соединение, выполнить `upgrade head`, выдать гранты на конкретные таблицы и проверить ревизию и эффективные права до commit. Зависит от 2.2, использует тесты 1.2–1.4. Связь: AC-PG-001 / SC-PG-001, SC-PG-002, AC-PG-002 / SC-PG-003, AC-RUN-001 / SC-RUN-001. Готово, когда миграция, grants и ревизия наблюдаются вместе после commit и исчезают вместе при внедрённом отказе. Повторная миграция сохраняет данные и права.
- [x] 2.4 Провести локальную проверку запуска и безопасного обновления по D-PG-01–03. Зависит от 2.3 и 3.3, использует тесты 1.2 и 1.3. Связь: AC-PG-001 / SC-PG-001, SC-PG-002. Готово, когда подтверждены явная остановка API до DDL, запуск мигратора целевого образа и блокировка старта при ошибке. Отметки этапов подтверждают `90 с` на старт, из них до `40 с` на PostgreSQL, `30 с` на мигратор и `15 с` на API. Проверить параметры `pg_isready` (`2 с` между попытками, `1 с` на попытку), настройки мигратора `lock_timeout=3 с` и `statement_timeout=15 с` и ненулевой exit при превышении бюджета процесса. Это проверка PR 2. Эксплуатационный runbook остаётся в PR 3.
